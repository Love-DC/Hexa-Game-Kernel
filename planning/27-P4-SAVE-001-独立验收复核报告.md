## 二、三项格式规则冻结（本次复核的核心交付）

三项规则在实现时采用、本次复核确认**端到端一致**，现予**冻结**。冻结含义：`SAVE-002` 及后续任务**直接复用**，如需变更须走独立裁决；本报告不修改任何一处。

### R-FMT-1 `save_id`

- **规则：** `^[a-z0-9]+(?:[._-][a-z0-9]+)*$`，长度 1–128（ASCII 字节）。语义 = 一个或多个小写字母/数字段，段间以**单个** `.`、`_` 或 `-` 连接；**不得**以分隔符开头/结尾，**不得**出现连续分隔符。
- **三处一致：**
  | 位置 | 证据 |
  |---|---|
  | JSON Schema | `schemas/save-manifest-v1.schema.json:49-54`（`$defs.save_id`，`pattern` + `minLength/maxLength`） |
  | 实现 | `crates/save-manager/src/lib.rs:700-721`（`is_valid_save_id`，逐字节扫描；`/save_id` 语义校验在 `:442-447`） |
  | 测试 | `src/lib.rs:824-834`（单元 `save_id_rules`）、`tests/manifest_contract.rs:416-424`（`invalid_save_id_is_rejected`）、`tests/manifest_contract.rs:302-334`（schema 与 Rust 双轨同拒） |
- **一致性判定：** ✅ 完全一致（schema 与 Rust 编码同一条正则语义；测试同时覆盖正例与反例）。

### R-FMT-2 时间戳（`created_at` / `last_saved_at`）

- **规则：** `^[0-9]{4}-[0-9]{2}-[0-9]{2}T[0-9]{2}:[0-9]{2}:[0-9]{2}(?:\.[0-9]+)?Z$` —— RFC 3339 **UTC**，仅接受 `Z` 后缀（**不接受** `+08:00` 之类偏移），小数秒可选。
- **Rust 层额外约束（值域）：** `month ∈ [1,12]`、`day ∈ [1,31]`、`hour ≤ 23`、`minute ≤ 59`、`second ≤ 60`（允许闰秒 60）。
- **三处一致：**
  | 位置 | 证据 |
  |---|---|
  | JSON Schema | `schemas/save-manifest-v1.schema.json:55-58`（`$defs.timestamp`） |
  | 实现 | `crates/save-manager/src/lib.rs:723-773`（`is_valid_timestamp`） |
  | 测试 | `src/lib.rs:836-846`（单元 `timestamp_rules`）、`tests/manifest_contract.rs:426-442`（`invalid_timestamp_is_rejected`）、`:302-334`（双轨同拒） |
- **一致性判定：** ✅ 一致。分层清晰：schema 管**语法**（形状），Rust 管**值域**（时间字段取值范围）。二者为「必须同时通过」关系，因此 Rust 严格于 schema 不构成冲突。

### R-FMT-3 SHA-256 摘要（`integrity.root_hash`）

- **规则：** 恰好 **64 位小写十六进制**（`[0-9a-f]{64}`）；规范示例占位值 `IMPLEMENTATION_GENERATED` **必须被拒绝**；`SAVE-001` 只承载不生成（生成属 `SAVE-003`）。
- **三处一致：**
  | 位置 | 证据 |
  |---|---|
  | JSON Schema | `schemas/save-manifest-v1.schema.json:85-93`（`$defs.integrity`：**仅**约束 `type=string`、`minLength=1`、`maxLength=256`；**未编码 64-hex**） |
  | 实现 | `crates/save-manager/src/lib.rs:775-780`（`is_valid_root_hash`，64 位 + 小写 hex）；占位拒绝 `:541-546`；格式拒绝 `:547-552` |
  | 测试 | `src/lib.rs:848-854`（单元 `root_hash_rules`：64✅ / 63❌ / 大写❌ / 占位❌）、`tests/manifest_contract.rs:161-165`（规范示例因占位被拒）、`:389-404`（占位与空值被拒） |
- **一致性判定：** ⚠️ **端到端一致，但强制层与另两项不同**：摘要格式**只由 Rust 层强制**，schema 仅做长度容器（1–256）。
  - 设计意图依据：schema `description`（`:5`）已声明「value-level semantics … are enforced by the Rust layer」，并把 `placeholder root_hash`、`integrity algorithm` 列为 Rust 层职责。
  - **判定：属既定分层设计，非实现缺陷**（理由：`algorithm` 是独立字段，schema 若硬编码 `{64}` 会与未来算法解耦失效）。但 `description` 的枚举**未包含「摘要格式」本身**，见 §七 F-2。

### 三项规则总表

| 规则 | 语法由谁强制 | 值域/语义由谁强制 | schema 侧 | Rust 侧 | 测试覆盖 | 结论 |
|---|---|---|---|---|---|---|
| R-FMT-1 `save_id` | Schema + Rust | Rust | `pattern` | 逐字节扫描 | 正+反+双轨 | ✅ 一致 |
| R-FMT-2 时间戳 | Schema + Rust | Rust（月/日/时/分/秒值域） | `pattern` | 逐字节扫描 + 值域 | 正+反+双轨 | ✅ 一致 |
| R-FMT-3 `root_hash` | **Rust only** | Rust | 仅长度 1–256 | 64 位小写 hex | 单元 + 契约反例 | ⚠️ 一致但有分层说明建议 |

**已知且接受的限制（不修改）：** 时间戳未校验日历合法性（如 `2026-02-30T…Z` 会被接受）。规范只要求格式正确，且生成端为受控实现；保留现状，如需收紧属 `SAVE-003` 生成端职责。

## 三、`logical_tick` 对 `kernel-core::Tick` 的依赖评估

### 事实与证据

| 项 | 证据 |
|---|---|
| 唯一用途 | `crates/save-manager/src/lib.rs:38` `use kernel_core::Tick;`；`:372` `pub logical_tick: Tick`。除此**无其它 `kernel-core` 类型**被使用（`cargo metadata` 实测 `save-manager` 对 `kernel-core` 的依赖仅此一项） |
| 依赖声明 | `crates/save-manager/Cargo.toml:10` `kernel-core = { path = "../kernel-core" }` |
| `Tick` 定义 | `crates/kernel-core/src/lib.rs:15-16`：`#[derive(Clone, Copy, Debug, Default, Deserialize, Eq, Ord, PartialEq, PartialOrd, Serialize)] pub struct Tick(pub u64);` —— **透明 newtype**，serde 按内层 `u64` 序列化 |
| JSON 契约 | `schemas/save-manifest-v1.schema.json:31`：`"logical_tick": { "type": "integer", "minimum": 0 }` |
| 透明性实证 | `tests/manifest_contract.rs:39-55` 的规范示例写作 `"logical_tick": 72000`（整数），`from_bytes` 通过 schema 与类型化反序列化，仅因占位 `root_hash` 在**语义层**被拒（`:161-165` 断言 `save.invalid_field` @ `/integrity/root_hash`）→ 证明 `Tick(72000)` 与整数 `72000` 双向一致 |
| 架构许可 | `Project Architecture v1.0` §4.2 允许平台 crate 依赖 `kernel-core`；`save-manager → kernel-core` 正是 R-13 已裁定的依赖方向 |
| 边界实测 | `kernel-core -> []`（无任何工作区内部依赖）；`save-manager -> [kernel-core]`；`game-platform -> [kernel-core]` |

### 两个方案的证据对照

| 方案 | 变更足迹 | JSON/Schema 影响 | 收益 | 代价 / 风险 |
|---|---|---|---|---|
| **A. 保留 `kernel-core::Tick`（推荐）** | 无 | **零**（透明 newtype 已与整数等价） | ① 时间语义与内核唯一的逻辑时间**类型级对齐**，杜绝「秒 vs tick」类误用；② 保持 R-13 声明的依赖边为**真实有效**而非空悬；③ `kernel-core` 依赖极轻（仅 serde/sha2/thiserror），不引入沉重耦合 | 存档模型不再是「零依赖纯数据」，复用到非内核宿主时需携带 `kernel-core` |
| **B. 改为 `u64`** | 改 `lib.rs:38/372` 两处 + 测试 `Tick(72000)` → `72000`（2 处） | **零**（JSON 与 Schema 完全不变） | 彻底解耦，`save-manager` 成为零工作区依赖的纯数据 crate | 失去类型级时间语义；R-13 的依赖边失效（需同步更新 `planning/22` 措辞） |

### 推荐方案

**推荐 A（保留 `kernel-core::Tick`）**，理由按强度排序：
1. **语义正确性**：存档中的 `logical_tick` 与内核世界时间是**同一个概念**，用同一类型可编译期防止量纲错配；改成 `u64` 会把这个保证降级为约定。
2. **零序列化成本**：`Tick(pub u64)` 为透明 newtype，JSON 与 Schema 一字不改，选 A 不产生任何兼容性负担。
3. **与既有裁决一致**：R-13 已裁定方向为 `save-manager → kernel-core`，A 使该裁决有实际承载，不需要重开裁决。
4. **依赖代价低**：`kernel-core` 自身 `-> []`，不拉入 wasmtime 等重依赖。

**若负责人倾向「存档格式模型应零依赖」**：切换 B 亦为**零兼容成本**（JSON/Schema 不变），仅需同步更新 `planning/22` R-13 措辞。本次**不修改**，待裁决。
