## 一、目标

依据 `Mod Platform Specification v1.0` §7.1 与 §7.3，为 Platform 层补齐两件在 GK-P3-04 之后仍然缺失的能力：

1. **Mod 生命周期状态机**：以可观察、可诊断的方式承载 §7.1 的十个状态，并拒绝非法状态转换。
2. **System 注册协调器**：把 Platform 生产代码的 System 注册收敛到单一入口，先做完整预校验、再真实注册，并且**只在真实注册成功后**才把 Mod ID 写入已注册 ID 记录。

## 二、实现内容

### 2.1 生命周期状态机

新增类型（均在 `crates/platform-core/src/lib.rs`）：

- `ModLifecycleState`：§7.1 的十个状态 —— `Discovered`、`Validated`、`Resolved`、`Loaded`、`Initialized`、`Active`、`Stopping`、`Stopped`、`Unloaded`、`Failed`。
  - `as_str()` 返回与规范完全一致的拼写。
  - `can_transition_to(next)` 是唯一的转换合法性判定入口。
  - `is_terminal()` 标记本实现的保守终止集合。
- `ModLifecycle`：单个 Mod 的状态载体，持有 `mod_id`、当前 `state` 与已接受转换的 `history`。
  - `discovered(mod_id)` 从 `Discovered` 起始。
  - `transition(next)` 非法时返回可诊断的 `PlatformError::Lifecycle`，且**当前状态保持不变**。
  - `fail()` 从任意非终止阶段进入 `Failed`。

转换表（本实现）：

| 当前状态 | 允许到达 |
| --- | --- |
| `Discovered` | `Validated`、`Failed` |
| `Validated` | `Resolved`、`Failed` |
| `Resolved` | `Loaded`、`Failed` |
| `Loaded` | `Initialized`、`Failed` |
| `Initialized` | `Active`、`Failed` |
| `Active` | `Stopping`、`Failed` |
| `Stopping` | `Stopped`、`Failed` |
| `Stopped` | `Unloaded`、`Failed` |
| `Unloaded` | 无（本实现保守拒绝） |
| `Failed` | 无（本实现保守拒绝） |

**规范缺口标注**：§7.1 只说 `Failed` 为“可从多个阶段进入的错误状态”、`Unloaded` 表示“运行实例及其平台资源已经清理完成”，并未给出二者的出边。因此上表中 `Unloaded`/`Failed` 无出边是**本实现的保守策略**，不得表述为“规范已定义其为终止态”。若后续规范明确出边，改动点集中在本表与 `terminality_is_conservative` 相关测试。

**`Disabled` 处理**：§7.1 未把 `Disabled` 列入状态枚举，也未给出其转换。本实现**不新增** `Disabled` 变体，也**不把 `Stopped` 等同于 `Disabled`**，将其标记为待定义项而非擅自扩展规范。

### 2.2 注册协调器

新增 `ModRegistry`：

- 内部仅持有 `BTreeSet<String>`（已成功注册的 Mod ID 集合），与生命周期状态**职责分离**（`ModLifecycle` 只管状态，`ModRegistry` 只管注册记录）。
- `registered_ids()` / `registered_count()` / `contains(id)` 为只读观察接口。
- `register_batch(&mut self, kernel: &mut Kernel, systems: Vec<(String, Box<dyn System>)>) -> Result<(), PlatformError>`：
  - 输入为**移交所有权的消费型** `Vec<(String, Box<dyn System>)>`，不使用无法移交所有权的借用切片。
  - **阶段一（预校验，不触碰 Kernel）**，按序检查：
    1. 批内重复 Mod ID → `platform.lifecycle.duplicate_mod_id`
    2. 声明 ID 等于 `System::id()` → 否则 `platform.lifecycle.mod_id_mismatch`
    3. 与历史已记录 ID 冲突 → `platform.lifecycle.already_registered`
    4. Kernel 自身的 ID 规则 —— **直接复用 `kernel_core::validate_type_id`**，不复制维护第二套可能漂移的规则 → 否则 `platform.lifecycle.invalid_mod_id`
  - **阶段二（真实注册）**：仅当阶段一全部通过，才逐个调用 `Kernel::register_system`；每个成功返回 `Ok` 之后**立即**把该 ID 写入记录；Kernel 若在真实注册时拒绝，返回 `platform.lifecycle.registration_rejected`。

### 2.3 错误类型

沿用既有错误约定，不新建错误基础设施：

- 新增 `PlatformError::Lifecycle(Box<LifecycleFailure>)` 变体，配套私有构造器 `PlatformError::lifecycle(...)`，装箱理由与 `dependency`/`lock`/`api_catalog` 一致。
- 新增 `PlatformErrorCode::Lifecycle` → 稳定错误码 `platform.lifecycle`。
- 新增 `LifecycleCode`（六个稳定子码）与 `LifecycleFailure`（携带 `code`、`mod_id`、`from`、`to`、`batch_index`、`message`），`message` 仅诊断用途，非机器协议。

### 2.4 生产注册路径收敛

`crates/platform-core/src/main.rs` 中两处直接 `kernel.register_system(...)`（原第 29、54 行）改为经 `ModRegistry::register_batch` 注册：

- `demo` 主路径与快照恢复路径各自持有独立的 `ModRegistry`，保证记录的 ID 集合与各自 Kernel 的真实接受状态一致。
- 测试代码中的直接注册路径**未改动**（`tests/p1_vertical_slice.rs` 保持一致），不为统一入口而大范围改写既有测试。

## 三、一致性边界（重要）

`ModRegistry` 只能约束**经由它自身**提交的注册。它**无法发现、也无法阻止**外部直接调用 `Kernel::register_system()`；直接调用不会更新协调器记录，协调器亦无感知。因此：

- 本方案对**单次提交批次**给出的保证是**条件性**的（见 `planning/13-P3-05-R1-V1修复报告.md`）：对**干净 Kernel**（只含经协调器注册的 System），本批次预校验与注册失败时不留半注册组合；但若目标 Kernel 已存在**绕过协调器**直接注册的 System，协调器无法感知，批次仍可能在更早元素已提交后于中途失败。R1 已通过冻结身份修复消除 `System::id()` 不稳定引起的部分注册。
- 该保证**不是** Kernel 提供的通用事务或回滚能力，也**不构成**“全局注册一致性已保证”的声明。
- 已知旁路限制由 `bypass_boundary_direct_kernel_registration_does_not_update_the_record` 测试显式记录为**已知限制**。
- 不新增 CI 扫描脚本；Platform 自身的旁路通过生产入口约束、测试与代码评审控制。
