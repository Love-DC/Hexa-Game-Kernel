## 一、摘要定义域：精确覆盖哪些字节（回答 Q1）

### 1.1 分区摘要域（`partition_digest`）

```
partition_digest = SHA-256( PARTITION_DIGEST_DOMAIN ‖ partition_record(p) )
```

`partition_record(p)` **逐字节等同于** `SaveLayout::to_bytes()` 中 `encode_partition` 写出的那一段（`partition.rs:748-800`；**不含 `index`**，`index` 仅出现在错误路径指针里）：

```
kind_tag: u8                                  // Manifest=0, World=1, Mod=2, Metadata=3, Integrity=4
[ ns_len: u16be ‖ ns_utf8 ]                   // 仅当 kind_tag == 2（Mod）
owner_tag: u8                                 // SaveSystem=0, Kernel=1, Mod=2
[ owner_ns_len: u16be ‖ owner_ns_utf8 ]       // 仅当 owner_tag == 2
schema_flag: u8                               // 0 = 无；1 = 有
[ schema_len: u16be ‖ schema_utf8 ]           // 仅当 schema_flag == 1
payload_len: u32be ‖ payload_bytes
```

**A2 要素对应：**

| A2 要素 | 覆盖字段 |
|---|---|
| **分区身份** | `kind_tag` + Mod 命名空间 |
| **必要元数据** | `owner_tag`（+ Mod 所有者命名空间）、`schema_flag`/`schema_version`（`schema_flag` 使 `None` 与 `Some("")` 可区分） |
| **载荷内容** | `payload_len` + `payload_bytes`（长度前缀使「空载荷」与「缺失载荷」可区分） |

**要点：**
1. **不覆盖 `index`**：分区摘要是「分区自身的函数」，不是「位置的函数」。
2. **不覆盖 Integrity 分区**：生成与校验**在计算前先剔除** `SavePartitionId::Integrity`（A1）。仅含 Integrity 的布局等价于空布局（§3）。
3. **各分区取什么字节（冻结）：**
   - `Manifest` 分区：载荷取**规范化字节 CMB**（§1.3.2）——**唯一例外**，原因是自引用（§1.3）。
   - `World` / `Mod(ns)` / `Metadata` 分区：载荷取**布局中存储的不透明原始字节**（`partition.payload.as_bytes()`，**不解析、不重编码、不规范化**），见 §1.3.9。
   - 所有分区的 `owner` / `schema_version` 一律取**存储值**（不派生、不推断）。
4. `SaveLayout::get(id)` 可用于定位分区；但 SAVE-003 **不信任** `SaveLayout.partitions` 的存储顺序（该字段为 `pub`，SAVE-002 登记的 **P-3**），一律经 `to_bytes()`（内部重排）或显式规范序处理（§2）。

### 1.2 根哈希域（`root_hash`）

```
root_hash = SHA-256( ROOT_DIGEST_DOMAIN ‖ SaveLayout::to_bytes( layout ∖ {Integrity}, Manifest.payload := CMB ) )
```

- **复用** `partition.rs:593-622` 的 v1 编码（`"SL"` + `u8 version=1` + `u32be count` + 记录序列），**不新增字节格式**（v1 已被 `partition_contract.rs:679-711` 金标测试逐字节固定）。
- 剔除 Integrity **必然改变 `count`**，故实现必须**重新编码**（不是从原流中切掉一段）。
- 覆盖成员：`Manifest`（载荷 = **CMB**）、`World`、所有 `Mod(ns)`、`Metadata`；**不含** `Integrity`。
- 编码前 `Manifest` 分区的 `owner`（`SaveSystem`）与 `schema_version`（`None`）**按存储值**参与记录编码。

**域标签（冻结；长度已实测校正）：**

```
PARTITION_DIGEST_DOMAIN = b"GKSAVE-PARTITION-DIGEST-v1" ‖ 0x1F   (27 字节，含 0x1F)
ROOT_DIGEST_DOMAIN      = b"GKSAVE-ROOT-DIGEST-v1"      ‖ 0x1F   (22 字节，含 0x1F)
```

- **`DESIGN-02` 勘误：** 上一稿正文写作 28 / 23 字节，与 ASCII 实际长度（26+1 / 21+1）**不符**。本稿以实测值 **27 / 22** 为准。两者均已用真实实现落盘复核（见 §7.1 / §7.2 的完整 hex）。
- `0x1F`（ASCII US）作终止符，确保与 SAVE-001 的 manifest 序列化、kernel `state_hash`（`game-kernel-world-state-v2\0`）、platform `content_digest` **不可能同域碰撞**。

### 1.3 【D-1】Manifest 自引用与规范化字节（CMB）

#### 1.3.2 CMB 的精确定义

```
CMB(manifest_partition_payload) =
    SaveManifest::to_bytes(
        m := SaveManifest::from_bytes(manifest_partition_payload)?
        m.integrity := INTEGRITY_DIGEST_SENTINEL
    )

INTEGRITY_DIGEST_SENTINEL = Integrity {
    algorithm: SUPPORTED_INTEGRITY_ALGORITHM,   // = "sha256"（编译期常量，非调用方可控）
    root_hash: "0" × 64,                        // 固定 64 个 '0'（形状合法：64 位小写 hex）
}
```

- **前置条件（冻结）**：`from_bytes` 是**完整校验型**入口（required-field → schema → 类型化反序列化 → `validate()`）。因此 CMB **只对「完全合法的 Manifest」有定义**；任何不合法 Manifest 都会在此之前失败关闭（§1.3.8）。
- **豁免对象 = 整个 `integrity` 成员**：其内容被替换为**编译期常量**，因此**任何存储的 `integrity` 取值都不是摘要的输入**——这正是「`integrity` 成员本身不纳入其所保护的字节」的精确实现。
- **常量哨兵 vs 字面删除（等价性论证）**：把成员替换为固定常量与把成员**删除**，对摘要的安全性**完全等价**——两者都使 `business_fields ↦ digest` 成为纯函数，固定常量后缀不引入任何调用方可控输入，映射的单射性不受影响。选择「常量哨兵」而非「字面删除」的原因是**工程稳健性**：它直接复用 SAVE-001 冻结的、**与 `serde_json` 特性无关的**字段序序列化器；字面删除需要走 `to_value()` → `remove("integrity")` → `serde_json::to_vec`，其对象键序取决于 `serde_json` 的 `preserve_order` 特性（本工作区该特性**未启用**，键按字典序），属**第二套规范化**（见 §10 备选 B-α′）。
- **自一致性证明（关键；已实测）**：CMB **不依赖** `root_hash` 的取值 ⇒ `root_hash(layout with root_hash=X) == root_hash(layout with root_hash=Y)` 对任意 X、Y 成立。实测：`root_hash` 取 `0123…cdef` 与 `fff…fff` 两种取值时，真实实现产出的 CMB **逐字节相同**（§7.1 步骤 ③）。
- **解析失败**：若 Manifest 分区载荷不是合法 Manifest JSON，`SaveManifest::from_bytes` 的 SAVE-001 错误**原样传播**（不重包装、不新增码）；若布局中没有 Manifest 分区 → `save.integrity_missing`（§5.3）。

#### 1.3.3 不破坏 SAVE-002 不透明载荷契约

- SAVE-002 的契约是「**承载**时不解释、不原地重编码」；SAVE-003 **只读地**从 Manifest 分区字节**派生**一份用于哈希的规范化视图，**从不写回**布局的任何分区载荷。
- 布局中 Manifest 分区仍保存原始不透明字节；其余分区（World / Mod / Metadata）**完全不解析**，其记录直接取存储字节 → B-1/B-3 不透明承载**原样保持**（§1.3.9）。
- **类型级证据（本稿新增）**：SAVE-003 的全部入口一律取 **`&SaveLayout`**（不可变借用），签名上**不可能**修改传入的布局（§1.3.10）。「只读」不是靠约定，而是由**借用检查器**保证。
- **实测证据**：同一布局对象连续两次 `to_bytes()` 逐字节相同、分区载荷原样保留（§7.1 步骤 ④）。

#### 1.3.4 授权影响

**不需要扩大实现文件授权范围。** 规范化只使用 SAVE-001 已有的 `pub` 字段与 `pub` 方法，`lib.rs` 仅需 `+1` 行模块注册（§12）。SAVE-001 的代码与行为**零改动**。

#### 1.3.5 【`DESIGN-03` 冻结】常量哨兵规则与影响范围

`DESIGN-02` §1.3.5 把「哨兵 vs 字面删除」列为待签字细项。本稿**冻结**如下，并把该细项从「二选一」收紧为**一个确定的字节规则**：

> **冻结规则（`M-α′`）：** CMB 生成时，`integrity` 成员被整体替换为**值替换**——
> `algorithm` 保留**解析所得的原值**，`root_hash` 固定为常量 `"0"×64`。
> 今日该形态与 `DESIGN-02` 的「整成员常量」**逐字节等价**（见下「等价性」）。

**① 替换整个 `integrity` 成员的影响范围（逐子字段）**

| 子字段 | 是否纳入摘要 | 影响与安全性论证 |
|---|---|---|
| `integrity.root_hash` | **否**（被常量替换） | **必须排除**：它是摘要自身，纳入即自引用（§1.3）。排除后 `business_fields ↦ digest` 成为纯函数，且生成/校验稳定复算（实测见 §1.3.2） |
| `integrity.algorithm` | **否**（`M-α′` 下按原值写出，实值恒为 `"sha256"`） | **无信息损失**：SAVE-001 `validate()` 强制 `algorithm == "sha256"`（`lib.rs:534-542`），故任何**可达**的 CMB 在该位置的字节**必然**是 `"sha256"`。⇒ 「整成员常量替换」与「仅替换 `root_hash`」**今日产出相同字节** |

**② 等价性（实测）**：`M-α′` 与 `DESIGN-02` 的整成员常量替换，在 **G6 向量**上产出的 CMB 均为同一 493 字节（§7.2，真实实现逐字节验证）。差异仅在**未来**：若某版本引入第二种合法算法，整成员常量替换会把 `algorithm` 钉死为 `"sha256"`，使「仅改算法」的篡改**不进 CMB**（降级风险）；`M-α′` 保留原值 ⇒ 该篡改仍改变 CMB。

**③ 未来约束（登记，非阻断）**：`M-α′` 的安全性依赖「`algorithm` 可被写入 CMB」。若某版本放开多算法，`SAVE-003` 的实现**必须**继续保留 `algorithm` 原值（不得退回整成员常量），并同步评估 `SC` 载荷与 R-FMT 规则。该约束须随 `SAVE-003` 编码写入模块文档。

**④ 影响范围之外**：`M-α′` 不改 `SaveManifest`/`Integrity` 的类型、不改 `to_bytes`、不改 §1.2 的域标签、不改 `SC` v1 布局、不改任何冻结的 R-FMT 规则。

**(c) 保护级别（边界，必须显式声明）**

CMB 是 **canonical-semantic（规范语义级）** 覆盖，**不是原始字节级**覆盖：

- **必然如此**：原始字节含 `root_hash` ⇒ 原始字节级覆盖 = 自引用，不可实现。
- **语义为零的差异不被检出**（空白、键序、转义写法、被遮蔽的重复键）：这是**期望行为**——它们不承载语义，且规范化后**收敛为同一 CMB**（实测：全反序键序 + 换行缩进的 Manifest 与规范输入产出**逐字节相同**的 CMB）。
- **`mods[]` 顺序被保留**（`Vec` 序即「记录的 Mod 清单顺序」，是语义的一部分）。A3 只要求**分区（SaveLayout）插入顺序**无关，**不**要求 `mods[]` 顺序无关；本稿不重排 `mods[]`。
- **任何语义变化都被检出**（E3）。

#### 1.3.7 【`DESIGN-03`】非规范输入与结构异常的处理规则（全部经真实实现实测）

#### 1.3.8 【`DESIGN-03`】失败关闭（fail-closed）证明

> **不变量 F-1：** 不存在任何输入使 `verify` 产出「`Ok(report)` 且 `is_intact() == true`」而实际未被验证。

**控制流证据（编码阶段须逐条落实并测试）：**

| # | 机制 | 保证 |

| F-1b | `expected_root` 唯一来源 = `SaveManifest::from_bytes(Manifest 分区载荷)?.integrity.root_hash`（`?` 传播） | 载荷不可解析 ⇒ `Err(SAVE-001 码)`；**不**产生 `Intact` |

**真空真（vacuous truth）风险已被 F-1e 明确封堵**：由于 D-8 冻结「Manifest 亦出具条目」，且 `verify` 要求 Manifest 分区存在，`partitions` 非空是必然；`!is_empty()` 为**冗余保险**，须在实现中保留。

#### 1.3.9 【`DESIGN-03`】其他分区为何继续使用原始逻辑字节

| 分区 | 摘要输入 | 为什么不规范化 |
|---|---|---|
| `World` | **存储的不透明快照字节**（`B-1`：`Kernel::snapshot()` 原样字节） | 其格式归 kernel；SAVE-003 无解析权，也不得推断（`world_schema_version` 与 kernel `SNAPSHOT_FORMAT_VERSION` **无映射**） |
| `Mod(ns)` | **存储的不透明 Mod 载荷字节**（`B-3`） | 无平台 Mod 读写通道；解析即越界 |
| `Metadata` | **存储的不透明 session-data 字节**（`B-2`） | 同上，且无独立版本字段 |
| `Manifest` | **CMB**（规范化） | **唯一例外**，仅因自引用；且该规范化**只读派生**、不写回 |

**记录级编码**（`kind_tag`/`owner`/`schema_flag`/`schema_version`/`payload_len`）对所有分区一律使用**存储值**，因此「载荷字节不变但 `owner`/`schema_version` 被改」这类篡改同样会被检出（§7.3）。

#### 1.3.10 【`DESIGN-03`】SAVE-003 接口契约（冻结；编码阶段以契约测试锁定）


- **`generate` 不写回**：返回 `GeneratedIntegrity { root: String, checksums: Vec<u8> }`；由**调用方**（未来的 SAVE-004/005）填入 `Manifest.integrity.root_hash` 与 `SavePartitionId::Integrity` 载荷。

### 1.4 为什么不采用「分区摘要序列的再哈希」

## 二、如何保证分区插入顺序变化不影响摘要（回答 Q2）

**由三层机制共同保证，且可被测试证伪。**

1. **单一事实源排序**：`SavePartitionId` 的 `Ord`（`partition.rs:268-283`）定义规范序 `Manifest < World < Mod(ns) < Metadata < Integrity`，Mod 之间按命名空间字典序；`SaveLayout::new` 排序（`partition.rs:457-460`），`to_bytes` **再防御性排序**（`partition.rs:596-597`）。
2. **摘要域不含位置信息**：分区摘要覆盖**记录字节**而非「第 i 个分区」。
3. **根哈希只读规范序**：根哈希对规范序编码计算。

**实现约束（必须显式声明并测试）：**
- `SaveLayout.partitions` 是 `pub` 字段（SAVE-002 已登记的 **P-3**），调用方可构造**未排序**布局 → SAVE-003 **不得信任存储顺序**，一律经 `to_bytes()`（其内部已重排）。
- **反例实测**：早期 `DESIGN-01` 以 `{Manifest, World, Mod}` 三分区验证「未排序拼接的 6 种排列产出 6 个不同根」，证明顺序无关**不是自动成立**，必须由规范排序保证 → 纳入 T-6。

## 四、如何识别并报告所有摘要不匹配的分区（回答 Q4）—【`DESIGN-03` 修订】

**核心：一次校验遍历，不 fail-fast，返回完整发现清单**（规范 §12.3「必须明确指出哪些分区损坏」）；同时贯彻「只报告、不修复」。

### 4.1 报告模型（`DESIGN-03` 增补「根的比较三方」）

```rust
pub enum PartitionIntegrity {
    Verified,                                      // 期望存在且匹配
    Mismatch { expected: String, actual: String }, // 双方均 64 位小写 hex
    Missing,                                       // checksums 有条目，布局中无该分区
    Unexpected,                                    // 布局中有该分区，checksums 无条目
}

pub struct IntegrityReport {
    pub algorithm: String,                 // = "sha256"（复用 SAVE-001 常量）
    pub manifest_root: String,             // 权威期望：Manifest.integrity.root_hash
    pub checksums_root: String,            // SC 载荷内自述的根
    pub computed_root: String,             // 本次计算值
    pub root_matches: bool,                // computed_root == manifest_root
    pub checksums_root_matches: bool,      // checksums_root == manifest_root
    pub partitions: Vec<(SavePartitionId, PartitionIntegrity)>,   // 规范序；不含 Integrity 自身
}

impl IntegrityReport {
    pub fn is_intact(&self) -> bool {
        self.root_matches
            && self.checksums_root_matches
            && !self.partitions.is_empty()
            && self.partitions.iter().all(|(_, s)| matches!(s, PartitionIntegrity::Verified))
    }
    pub fn corrupted_partitions(&self) -> impl Iterator<Item = &(SavePartitionId, PartitionIntegrity)>;
}
```

### 4.2 为什么必须比较 `SC` 载荷自述的根（`DESIGN-02` 的一处漏洞）

`DESIGN-02` §6.1 的 `SC` v1 载荷**携带** `root_hash`，但 §4 的判定只看「`Manifest.integrity.root_hash` vs 计算值」与逐分区条目 ⇒ **该 `root_hash` 被解析却从不参与判定**，属**未验证字段**。后果：**只篡改 `SC` 载荷里的 `root_hash`（不动任何分区、不动 Manifest）会得 `Intact`**。

本稿封堵：把 `SC.root_hash` 纳入判定（`checksums_root_matches`）。判定所需的三方一致性为：

```
manifest_root == computed_root == checksums_root        （全部 64 位小写 hex）
```

> 与 D-4 删除死码同一纪律：**不保留「承载但不验证」的字段**。此处选择「使用它」而非「删掉它」，因为该字段使 `SC` 记录**自描述**（§8：SAVE-008 备份校验需要一份自带根的校验记录）。

### 4.3 判定语义（冻结）

| 条件 | 结果 |
|---|---|
| `manifest_root == computed_root == checksums_root` **且** 逐分区全部 `Verified` | **`Intact`**（`Ok(report)`，`is_intact() == true`） |
| 任一不等（含根不等 / `checksums_root` 不等） **或** 任一逐分区非 `Verified` | **`Mismatch`**（`Ok(report)`，`is_intact() == false`） |
| 无 Manifest 分区 / 无 Integrity 分区 | **`Unverifiable`** = `Err(save.integrity_missing)`（无期望值即无从判定） |
| Manifest 载荷不可解析 | `Err(SAVE-001 码)`（原样传播） |
| `SC` 载荷畸形 / 算法不支持 | `Err(save.integrity_payload_invalid)` / `Err(save.integrity_algorithm_unsupported)` |

### 4.4 「绝不误判 `Intact`」证明（C-1～C-6）

| # | 情形 | 结果 | 为何不可能为 `Intact` |
|---|---|---|---|
| C-1 | 无期望根（无 Manifest 分区） | `Err` | 报告对象未构造（F-1c） |
| C-2 | 无逐分区期望（无 Integrity 分区） | `Err` | 同上（F-1c） |
| C-3 | Manifest 不可解析 | `Err` | F-1b：`?` 在任何报告构造前传播错误 |
| C-4 | `SC` 载荷畸形 / 算法不支持 | `Err` | F-1d / §5.3 |
| C-5 | 内容损坏（字节/命名空间/`schema_version`/`owner`/增删/换位/Manifest 业务字段） | `Ok` + `Mismatch` | 摘要改变（E3、§7.3）⇒ `root_matches=false` 或条目非 `Verified` |
| C-6 | 仅篡改 `SC` 载荷的根，或仅篡改 Manifest 的 `root_hash` | `Ok` + `Mismatch` | §4.2 三方比较 ⇒ `checksums_root_matches=false` 或 `root_matches=false` |

**纪律：**
- 不修复、不删除、不自动改指、不覆盖（§4.4/§9.1/§16.5）。
- 报告顺序 = 规范序（可复现、可金标）。
- **结构性/前置性错误 → `Err`；校验发现（不匹配）→ `Ok(report)`**。二者不得混用，避免「把损坏当异常吞掉」。
- **Manifest 也出具分区条目（D-8 冻结：是）**，其 `partition_digest` 基于 **CMB**（§1.3）。

## 五、算法标识、摘要格式与错误分类（回答 Q5）

### 5.1 算法标识（D-6 冻结：**不新增枚举**）
- **复用** SAVE-001 冻结常量 `SUPPORTED_INTEGRITY_ALGORITHM = "sha256"`（`lib.rs:62`），**不引入第二种拼写**、**不新增公开枚举**（最小公开面，与 B-5 精神一致）。`IntegrityReport.algorithm` 为 `String`，取值恒等于该常量。

### 5.2 摘要格式（D-5 冻结）
- **内部计算**：原始 32 字节。
- **规范文本形式**：**64 位小写十六进制，无前缀**——严格等于冻结规则 **R-FMT-3**（`planning/26` §8.3）。
- ⚠️ **仅登记、不改动他处**：`platform-core` 的 `content_digest`/`config_digest` 用 `"sha256:<64hex>"` 带前缀风格，属**不同字段族**。SAVE 侧统一采用 无前缀 形式，**不修改** `platform-core`。

### 5.3 错误分类（D-4 冻结：**3 码**；本稿**更正触发条件描述**）

| 稳定码 | 触发条件（`DESIGN-03` 更正后） | 可达路径 | 结果 |
|---|---|---|---|
| `save.integrity_algorithm_unsupported` | `SC` 载荷内 `alg` ≠ `"sha256"` | **仅 `SC` 解析路径** | `Err` |
| `save.integrity_missing` | 布局**无 Manifest 分区**（无期望根）或**无 Integrity 分区**（无逐分区期望） | `verify`/`generate` 前置检查 | `Err`（= `Unverifiable`） |
| `save.integrity_payload_invalid` | `SC` 载荷畸形：错 tag / 未知 version / 截断 / 尾随字节 / 非法 hex / 大写 hex / 长度 ≠ 64 / 重复条目 / 乱序（非规范序）条目 / 含 `kind_tag == 4`（Integrity）条目 | **仅 `SC` 解析路径** | `Err` |

**`DESIGN-03` 对 §5.3 的更正（码集合**不变**，仅更正描述）：** `DESIGN-02` 把「Manifest `integrity.algorithm` ≠ `sha256`」列为 `save.integrity_algorithm_unsupported` 的触发条件，**不成立**：`SaveManifest::from_bytes` 的 `validate()` 先以 `save.invalid_field @ /integrity/algorithm` 拒绝（`lib.rs:534-542`；实测见 §1.3.7 末行），该码在此路径上**永不可达**。故：

- **Manifest 侧算法不支持** → 传播 SAVE-001 的 `save.invalid_field`（**不重包装**，与全篇纪律一致）。
- **`SC` 侧算法不支持** → `save.integrity_algorithm_unsupported`（**非死码**，T-13 覆盖该路径）。

**为何不删该码：** 它对应**独立**的 `SC` 载荷域，且在 T-13 上有可复现的触发输入；删去会把「算法不支持」与「载荷畸形」两件事混为一码，降低可诊断性。

**与既有码的不相交核验（实测）：** 既有 12 码 = SAVE-001 的 7 码（`save.invalid_manifest`/`save.missing_field`/`save.invalid_field`/`save.unsupported_format_version`/`save.invalid_mod_entry`/`save.duplicate_mod_id`/`save.invalid_schema`）+ SAVE-002 的 5 码（`save.invalid_partition`/`save.invalid_layout`/`save.invalid_namespace`/`save.partition_ownership_violation`/`save.duplicate_partition`）。上表 3 码均以 `save.integrity_` 起始；`grep -rn "save\.integrity" --include=*.rs crates` **实测无任何既有匹配** → **确认不相交**。

## 六、Integrity 分区内部载荷的确定性编码与解析（回答 Q6，D-3 冻结）

**A7：不发布公共 Schema，但定义内部确定性编码。** 采用与 SAVE-002 同族的**二进制、长度前缀、tag + version** 编码（**不新增 `schemas/` 文件**）。

### 6.1 `SC` v1 字节布局（字段顺序、端序、上限）

```
offset  field            encoding                        说明/上限
0       tag             b"SC"                (2B)        固定
2       version         u8 = 1                          未知版本 → 拒绝
3       alg_len         u16be               (2B)        上限 65535；实值 6
5       algorithm       UTF-8               (alg_len)   必须 == "sha256"
5+alg   root_hash       64 × ASCII 小写 hex (64B)       严格等于 R-FMT-3 文本
…       entry_count     u32be               (4B)        上限 u32::MAX（注释）
…       entries[…]:      每项：
          kind_tag      u8                              0/1/2/3；==4 → 拒绝
          [ns_len       u16be]                           仅 kind_tag == 2
          [namespace    UTF-8 (ns_len)]                  须为合法 Mod 命名空间
          digest        64 × ASCII 小写 hex (64B)
```

> **`root_hash` 字段的用途（`DESIGN-03` 冻结）**：它是该校验记录的**自述根**，`verify` 时**必须**与 `Manifest.integrity.root_hash` 及本次计算值三方一致（§4.2/§4.3）。**它不是**未验证字段。

> **摘要的字节表示（`DESIGN-03` 冻结，规范性）**：`SC` v1 内**所有**摘要（`root_hash` 与每个条目 `digest`）一律以 **64 个 ASCII 小写十六进制字符**（= R-FMT-3 的**文本**形式）存放，**不**存放 32 字节二进制。
> - **一致性论据**：本条与 §6.1 表格（`root_hash` / `digest` 均写为「64 × ASCII 小写 hex (64B)」）、规则 7 的 `MIN_ENCODED_CHECKSUM_ENTRY_LEN = 65`（= kind 1 + digest 文本 64）、以及 **T-10** 的「非法 hex / **大写 hex** / 长度 ≠ 64」负例**三者互相印证**。若改存 32 字节二进制，则 `MIN` 必须为 33、T-10 的 hex 类负例全部失效——即与已冻结文本**冲突**。
> - **收益**：`SC` 内自述根与 `Manifest.integrity.root_hash`（JSON 字符串）**同一文本形态**，三方比较无需编码转换；R-FMT-3 规则在每个摘要处**逐条校验**。
> - **本稿据此更正 `DESIGN-02` §6.3 的 G8 示例**（该示例的条目摘要实为 32 字节二进制，与其自身 §6.1 冲突）：按规范重算后 **G8 = 292 B**（§7.2）。替代形态见 §10 的 **B-ε**（未采纳）。

**规则（冻结）：**
1. **端序**：一切多字节整数**一律大端**（与 SAVE-002 v1 一致）。
2. **条目顺序**：**必须按 `SavePartitionId` 规范序**写出；解析时**拒绝乱序**（否则「同一逻辑载荷多种字节表示」破坏确定性）。
3. **重复项**：解析时**拒绝重复 `SavePartitionId`**。
4. **Integrity 自排除**：条目**一律不含** `kind_tag == 4`；出现即拒绝（A1）。
5. **不写 `index`**。
6. **未知版本**：`version != 1` → 拒绝（不尝试向前兼容解析）。
7. **长度守卫 + 预分配上限**（R3 纪律）：
   - 编码侧：`entry_count → u32::try_from`、`ns_len/alg_len → u16::try_from`，一律 `map_err` 不截断。
   - 解码侧：**先算** `max_encodable = remaining / MIN_ENCODED_CHECKSUM_ENTRY_LEN`，其中 **`MIN_ENCODED_CHECKSUM_ENTRY_LEN = 65`**（kind tag 1 + digest **文本** 64）→ `count > max_encodable` 直接拒绝，**再**分配，杜绝输入控制的预分配放大。
8. **承载方式**：该载荷作为 `SavePartitionId::Integrity` 的**不透明 payload bytes** 放入 `SaveLayout`（复用 SAVE-002 承载能力，**不改** SAVE-002 契约）。
9. **零 I/O**（延续 B-4）。

### 6.2 为什么不用「规范 JSON」

JSON 需额外固定键序 / 数字格式 / 转义细节，冻结面更大；二进制与 SAVE-002 v1 **同族**，便于复用守卫风格；且 JSON 极易诱发「顺手发布 Schema」，与 A7 相悖。（备选 B-β 见 §10。）

### 6.3 载荷金标

完整字节与摘要见 **§7.2**（**G8**：3 条目，**292 B**；**G9**：0 条目，79 B）。本稿不再给出任何截断 hex。

> **`DESIGN-02` 勘误（第四处）：** `DESIGN-02` §6.3 称 G8 为 196 B 且给出摘要 `e0adcc09…`，但那组字节的条目摘要用的是 **32 字节二进制**，与 §6.1「64 × ASCII 小写 hex」、`MIN_ENCODED_CHECKSUM_ENTRY_LEN = 65`、T-10 的 hex 负例**均不一致**。本稿按 §6.1 规范重算：**G8 = 292 B，SHA-256 = `818b98044fd8e1b924988e2225c578fbd2b00eec09311001e0b15e3664eeb3ee`**（三工具一致，§7.1(2)）。G9 原本即为 ASCII 形态，**未变**。

## 七、如何证明实现符合契约（回答 Q7）

### 7.3 篡改测试

逐项翻转并断言**摘要改变 + 报告指向正确分区**：载荷字节（**G7-world `World("w")` → G5 `World("W")`**，即 `0x77`→`0x57`）、命名空间、`schema_version`、`owner`、增删分区、交换两分区位置、**仅篡改 `SC` 载荷的 `root_hash`（→ `checksums_root_matches=false`）**、仅篡改 Manifest 的 `root_hash`（→ `root_matches=false`）。

### 7.4 往返与只读性

- `encode_payload → decode_payload` 语义相等（空 / 单 / 多条目、含 Mod 命名空间）；
- `generate → verify` 得 `Intact`；且**写回 `root_hash` 后根值不变**（§1.3.2 自一致性，专项测试 T-18）；
- `verify` **只读**：调用前后布局 `to_bytes()` 逐字节相同（T-14；并由 `&SaveLayout` 类型保证，§1.3.3）；
- 乱序 / 重复 / 含 Integrity 条目的载荷**必须**被拒（负例）。

### 7.5 无 I/O 与无 panic

静态断言 `save-manager` 源码不含 `std::io`/`std::fs`；禁 `catch_unwind`；定宽转换全部 `try_from().map_err()?`；解码预分配受 `remaining / 65` 约束。
