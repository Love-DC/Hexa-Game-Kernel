## 4. 已有的项目基线

以下内容是现有文件中明确写出的规划原则，尚不等于实现已达标：

1. Kernel 是按确定规则推进权威世界状态的最小运行时，不包含具体游戏玩法。
2. Kernel Core 的六个基础模块为 Time、Scheduler、System、World、Command、Event；外围 Platform 管理 Mod、权限、兼容性、诊断和联机适配。
3. 所有权威状态写入应经过 Command；Mod 通过公开 API、事件或数据契约协作。
4. 模拟结果应能在声明的兼容边界内重复验证；外部输入、随机数、状态哈希和数值语义必须受控。
5. 存档迁移必须可验证、可恢复并保护原始存档；缺失 Mod 的数据不得静默丢弃。
6. Mod 加载不等于每 Tick 执行；普通社区代码应受限运行，不可信原生代码不能仅靠进程内 API 约束宣称安全。
7. 300+ Mod 是要通过测量验证的目标场景，不是已证明的容量承诺。

## 5. 主要风险

| 优先级 | 风险 | 影响 | 建议处理 |
|---|---|---|---|
| P0 | 文档清单中 05–08 缺失，尤其多人、工程基线、统一路线图未成文 | 多人契约、研发流程和验收门槛无法对照；实现可能各自解释 | 先维护统一缺口清单；多人阶段开始前补齐多人规范；把路线图和治理状态放入本次交付。 |
| P0 | 没有 Git、源码、构建和 CI 基线 | 无法回滚、复现或验证实现；AI 无法可靠交付局部改动 | 第一阶段获批后先创建版本控制和最小自动检查，再写核心代码。 |
| P0 | Tick 级原子性与逐条命令提交并存，但核心失败时的回滚边界没有精确定义 | 可能出现状态已部分改变而 Tick 被报告失败，破坏存档和重放一致性 | 先把可观察提交点、缓冲区、失败回滚及故障注入用例定义清楚。 |
| P1 | 确定性范围、跨平台数值语义、Wasm 引擎与版本未冻结 | 重放或联机资格无法形成可测试承诺 | 先以单一参考运行环境做垂直切片；跨平台承诺以实测矩阵决定。 |
| P1 | Mod 故障隔离策略只给出原则，未定义坏 Mod、依赖方及必需规则如何处理 | 继续模拟可能遗漏权威操作，停机则可能扩大故障影响 | 明确隔离粒度、状态保留、暂停条件、恢复入口和诊断记录。 |
| P1 | Manifest、存档元数据、API、迁移器和锁文件只有示例或概念 | 多模块容易产生不兼容的字段、版本解释和错误语义 | 为每种格式建立唯一可校验 Schema，并用契约测试锁定。 |
| P1 | 300+ Mod、长期运行和性能预算没有硬件与工作负载基线 | 无法判断性能是否达标，也容易过早承诺容量 | 先定义可复现基准场景与测量指标，再报告实际结果。 |
