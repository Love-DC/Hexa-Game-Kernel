## 2. D1：迁移器清单与 `CompatibleWithMigration` 的可达性

### 2.1 依赖事实

- 规范 §5.2 判定输入 7 = "可用迁移器清单"；规范 §5.3 步 7 = "查找可用迁移路径"。
- planning/22 L88：迁移器**声明、链查找、循环/缺失检测**（含 GAP-24/25）归 SAVE-006；L224：SAVE-006 依赖 SAVE-005。
- 即：SAVE-005 必须能输出 `CompatibleWithMigration`，但链查找机制尚不存在。

### 2.2 候选方案比较

| 方案 | 内容 | 评价 |
|---|---|---|
| A. 调用方注入迁移器清单 | `env.migrators: &[MigratorDescriptor]`（SAVE-005 定义描述符类型），判定器做声明级匹配 | 判定器保持纯函数（与 SAVE-001~004 风格一致）；但"链查找"被部分前移到判定器，与 SAVE-006 职责重叠 |
| B. 稳定查询 trait | `trait MigrationQuerier { fn find_path(...) }`，SAVE-006 实现 | 接口重；trait 对象进入判定器签名；测试需 mock——与现有手工类型风格不符 |
| C. 清单恒空 | SAVE-005 阶段 `CompatibleWithMigration` 不可达 | **否决**：任务表 L87 要求四类结论与双层映射随本包冻结为契约测试，一类不可达则契约测试无法覆盖 |
| **D（已裁决采纳，§2.4）. 注入"迁移路径查询结果"** | 判定输入建模为枚举：`MigrationPath::{NotRequired, Available(Vec<MigrationHop>), Unavailable}`；清单→路径的转换（链查找）完整留在 SAVE-006 | 判定逻辑稳定且不依赖 SAVE-006 机制；SAVE-005 契约测试注入三值即可覆盖全部分支；SAVE-006 落地后由装配层填充 `Available`，SAVE-005 已冻结接口零改动 |

【推导建议 → 已裁决（§2.4）】采纳方案 D。`MigrationHop = { from_version, to_version, migrator_id }` 仅作报告展示用途，SAVE-005 不验证链的确定性/循环（SAVE-006 的 GAP-24 职责）。

### 2.3 判定与执行的区分

SAVE-005 只输出"存在已声明的迁移路径"这一判定结论与路径摘要；迁移的**执行**（含事务、回退、GAP-25）归 SAVE-006/007。【契约明示】§5.1 `CompatibleWithMigration` 的语义是"存在已验证且获授权的迁移路径"——"已验证且获授权"在 SAVE-005 阶段的落实方式为：调用方保证注入的 `Available` 路径已经过其自身验证，判定器不重复验证（边界写入契约）。

### 2.4 负责人裁决（已裁决 · 2026-10-18 · `GK-P4-SAVE-005-DESIGN-DECISION-01` 决策 2）

**裁决：采纳方案 D（注入"迁移路径查询结果"）。**

- SAVE-005 兼容性判定器接收调用方提供的迁移路径查询结果：`MigrationPath::{NotRequired, Available(Vec<MigrationHop>), Unavailable}`。
- 判定器不负责迁移链查找、迁移器注册或循环检测；迁移器注册与完整迁移链查找仍归 SAVE-006。
- 契约测试通过注入上述三种状态覆盖对应判定分支。
- **建模声明：** Save Spec §5.2 判定输入 7 的字面是"可用迁移器清单"；本文在判定器接口边界将其建模为"迁移路径查询结果"。这是**实现建模选择**，不是规范原文表述，已获负责人明示认可；不得伪称为规范原文。
- 不提前实现 SAVE-006 的任何机制。

## 3. D2：Mod 兼容性信息

### 3.1 判定所需输入（对照 §5.2 输入 4-6、8）

存档侧已有：`SaveManifest.mods: Vec<SaveModEntry{id, version, schema_version}>`【契约明示，SAVE-001】。

当前环境侧需要（每项注明来源）：

| 输入 | 来源建议 |
|---|---|
| 当前启用 Mod 集合：`id` / `version` / `schema_version` | 调用方注入（装配层从 platform-core `ModManifest`/`LoadPlan` 转换） |
| Mod 依赖声明（`Vec<ModDependency{id,version}>`） | 调用方注入（platform-core `ModManifest.dependencies`） |
| Mod 的 kernel_api 要求 | 调用方注入（platform-core `ModManifest.kernel_api`） |
| 当前平台版本 / Kernel API 版本 | 调用方注入（同 DC-7 时间戳风格：判定器不读环境） |

### 3.2 依赖方向【推导建议】

save-manager **不新增对 platform-core 的依赖**。依据：SAVE-001 模块注释仅授权 `save-manager → kernel-core`（R-13）；Save Spec §6.1 "Mod Platform 负责提供必要信息"描述的是**信息流**，由装配层完成类型转换后注入，可保持 save-manager 依赖面无新边。判定输入类型（`InstalledModInfo` 等）在 save-manager 内定义。【待裁决 → 已裁决（§3.4）】确认该依赖约束（方案：save-manager 自定义输入类型 vs. 允许 `save-manager → platform-core` 新依赖边）。

### 3.3 异常输入处理【推导建议】

- **重复 Mod ID**（环境侧或存档侧）：结构化输入错误，判定不开始（不产 `Blocked`，属调用方数据缺陷）。
- **存档侧 Mod 在当前环境缺失**：`Blocked` + 细化标记 `missing_dependency`（§5.4 第 4 行）。
- **环境侧多出存档没有的 Mod**：属"新增 Mod 加入旧存档"场景（§6 A/B/C 类），SAVE-005 仅按 §5.3 步 4-5 记录并进入判定；A/B/C 三类的完整策略归 SAVE-009，本包只做兼容性结论不做加入许可裁决。
- **版本字符串格式错误**（环境侧注入值）：输入校验错误（判定不开始）；存档侧格式错误不可能发生（SAVE-001 `from_bytes` 已全量校验）。
- **依赖不满足**（环境侧 Mod 的 dependencies 在环境集合内无满足者）：`Blocked` + `missing_dependency`。

### 3.4 负责人裁决（已裁决 · 2026-10-18 · `GK-P4-SAVE-005-DESIGN-DECISION-01` 决策 1）

**裁决：采纳方案①（save-manager 自定义输入类型）。**

- `save-manager` 定义自身需要的输入类型（如 `InstalledModInfo`）。
- 装配层负责将 `platform-core` 的信息转换为 `save-manager` 输入类型。
- 不新增 `save-manager → platform-core` 依赖边。
- **规范纪律：** 本裁决不视为对其他架构规范的修改授权；若实施中发现必须同步修订的规范条款，先向负责人报告具体条款及理由，经裁决后方可修订。

### 3.5 负责人裁决（已裁决 · 2026-10-19 · `GK-P4-SAVE-005-DESIGN-DECISION-05` · 事项 2：版本信息来源边界）

**裁决：判定所需版本信息一律由调用方注入；判定器不自行读取环境。`platform_version` 仅由装配层注入，禁止以 crate 版本等伪来源顶替。**

- `CompatibilityEnv.platform_version`：当前平台版本（SemVer），**仅由装配层注入**。工作区当前无权威平台版本来源（workspace `Cargo.toml` 无 `version` 字段）；装配层如何获得该值属装配层职责，**不得**以 crate 版本或其他伪来源顶替。

- 判定器保持纯函数：不读环境变量、不读文件、不读 crate 元数据（与 SAVE-004 DC-7 时间戳注入风格一致）。
- **效力标注：** 本款为本次负责人裁决确立的实现约束，不是现有规范原文；规范 §5.2 仅规定判定输入集合，未规定注入来源边界。

## 4. D3：加载 API

### 4.1 顺序（对齐规范 §5.3 与 SAVE-004 卡 L171）

```text
read 文件字节 (Io)
  → SaveLayout::from_bytes            (容器解析；失败=结构损坏)
  → verify(layout)                    (完整性；不 intact ⇒ Corrupted，到此为止)
  → SaveManifest::from_bytes          (Manifest 分区负载解码)
  → system_manifest(layout)           (SM v1 加载侧验证；Missing/Invalid 两码)
  → 兼容性判定 (纯函数，见 §5)
```

【契约明示】`verify` 先于一切负载解码；**`Corrupted` 时 Manifest 与任何分区负载均不解码、不返回**——`InspectedSave` 只在 `is_intact()` 为真后构造（构造即证据）。

### 4.2 候选签名（全部基于 §1.1 既有类型）

```rust
/// 解析 + 完整性验证 + Manifest/SM 加载侧校验。不做兼容性判定。
pub fn inspect_save(bytes: &[u8]) -> Result<InspectedSave, LoadError>;

/// 便捷 I/O 入口：读文件 → inspect_save。唯一新增的文件读取点。
pub fn inspect_save_file(path: &Path) -> Result<InspectedSave, LoadError>;

/// 纯兼容性判定：无 I/O、无副作用、可重复（§5.2"判定结果必须可重复"）。
pub fn assess_compatibility(
    inspected: &InspectedSave,
    env: &CompatibilityEnv,
) -> Result<CompatibilityReport, CompatInputError>; // 输入错误结构化返回，判定不开始（OWNER-APPROVAL-01 B-3）
```

```rust
pub struct InspectedSave {
    layout: SaveLayout,            // 私有；经只读访问器暴露
    manifest: SaveManifest,        // get 访问器
    system_ids: Vec<String>,       // get 访问器
    integrity_report: IntegrityReport, // get 访问器
    // 只读访问器还包括 world_payload() 与 mod_payload(mod_id)（OWNER-APPROVAL-01）
}

pub struct CompatibilityEnv {
    pub platform_version: String,                 // SemVer，当前平台；仅装配层注入，禁伪来源（§3.5）
    pub kernel_api_version: SaveFormatVersion,    // 当前 Kernel API；数值对精确匹配（§5.6 裁决 B）
    pub installed_mods: Vec<InstalledModInfo>,    // §3
    pub migration: MigrationPath,                 // §2 方案 D
    pub policy: LoadingPolicy,                    // {Normal, Strict} 穷尽冻结（§5.5）
}

pub struct InstalledModInfo {
    pub id: String,
    pub version: String,                 // SemVer；不作判定谓词，仅诊断（OWNER-APPROVAL-01 B-1）
    pub schema_version: SaveFormatVersion,  // 相等即过，不等查迁移（§5.6 裁决 B）
    pub kernel_api_requirement: String,  // MAJOR.MINOR；与当前 Kernel API 数值对精确匹配（OWNER-APPROVAL-01 B-2）

```

### 4.3 不暴露半初始化 World 的保证

【推导建议】SAVE-005 的公开面**不提供任何 World/Kernel 构造入口**：`InspectedSave` 只暴露"已验证字节"的只读访问（World 分区负载以 `&[u8]` 形式给出，B-1 不透明）；`Kernel::restore`（或等价物）的调用发生在调用方，且调用方只能在拿到完整 `CompatibilityReport` 并选择继续后执行。半初始化世界在类型上无法从本包流出。

### 4.4 `LoadError` 分类（风格对齐 SAVE-001~004 手工错误类型）

```rust
pub enum LoadError {
    Io { stage: LoadIoStage, path: PathBuf, source: std::io::Error }, // LoadIoStage 仅 { Read }
    Layout(PartitionError),            // SAVE-002 原样传播
    Manifest(SaveManifestError),       // SAVE-001 原样传播
    Integrity(IntegrityError),         // SAVE-003 结构性错误
    Corrupted(IntegrityReport),        // 摘要不匹配：不解码负载（唯一携带报告的出口）
    SystemManifest(SystemManifestError), // SM 加载侧 Missing/Invalid 的正式使用点
}
```

【推导建议】`Corrupted` 作为 `LoadError` 变体（结构/完整性失败使加载不可能），同时作为 `CompatibilityVerdict` 取值（§5.1）——两者并存：`inspect_save` 阶段的损坏走 `Err(LoadError::Corrupted)`；若未来存在"结构完整但策略判损坏"的路径则走 verdict。本阶段判定器不产生 `Corrupted` verdict（所有损坏在 inspect 阶段已截获），该 verdict 取值仅为契约完整性保留。【待裁决 → 已裁决（§4.5）】确认此单点损坏出口设计。

### 4.5 负责人裁决（已裁决 · 2026-10-18 · `GK-P4-SAVE-005-DESIGN-DECISION-01` 决策 3）

**裁决：采纳单点损坏出口。**

- 存档读取、结构解析及完整性验证阶段通过 `LoadError::Corrupted` 表达损坏。
- `CompatibilityVerdict` 类型保留 `Corrupted` 取值，以保持 §5.1 四类结论契约完整；但 SAVE-005 当前阶段的兼容性判定器**不主动产生** `Corrupted` verdict。
- 完整性验证失败后，不得继续向后暴露该损坏存档的 Manifest 或负载（§4.1"构造即证据"纪律随本裁决生效）。
- 不得向调用方暴露半初始化的 World（§4.3 的类型级保证随本裁决生效）。
- **效力标注：** 以上边界为**本次负责人裁决**确立的实现约束；不得声称它们是现有规范已经明确规定的全部细节（规范强制条款以 §1.3 清单为准）。

### 5.5 负责人裁决（已裁决 · 2026-10-19 · `GK-P4-SAVE-005-DESIGN-DECISION-05` · 事项 6：`LoadingPolicy` 形态与语义）

**裁决：`LoadingPolicy` 取穷尽两值枚举 `{Normal, Strict}`，随本包冻结；Strict 为迁移闸门。**

- **穷尽冻结规则：** 两值即全部；不得借"未来扩展"名义预留第三值或松散反序列化。
- **效力标注：** `LoadingPolicy` 的类型形态与上述语义为本次负责人裁决确立的**实现建模**；规范 §5.2 输入 10 仅要求"当前加载模式和安全策略"参与判定，未规定具体取值与改写规则，不得伪称为规范原文。

### 5.7 负责人裁决（已裁决 · 2026-10-19 · `GK-P4-SAVE-005-OWNER-APPROVAL-01`）

**裁决：终审及实施契约阶段六项补充裁决。**

- **B-1（Mod version 不作谓词）：** 采纳方案③——Mod 自身 `version` 不作为存档兼容性判定条件；兼容性由 `schema_version` 承载。`mod_version_incompatible` 原因码零触发保留，仅用于诊断。

- **B-3（输入错误接口）：** 批准 `Result<CompatibilityReport, CompatInputError>`，四变体：`DuplicateModId` / `InvalidVersionFormat` / `EmptyModId` / `ContradictoryMigrationInput`。判定不开始、不产 verdict。
- **B-4（Strict flags 终态）：** 批准方案①——Strict 拒绝迁移时最终 `Blocked`，flags := {`rejected`}，`reason_code = policy_rejected`；不修改规范。`needs_backup`/`may_lose_data` 按改写前管线结果计算；`may_auto_continue = false`。
- **B-1a（依赖 VersionReq）：** 批准沿用 `platform-core` 先例——依赖 `version_requirement` 采用 SemVer `VersionReq` 求值；非法表达式归入 `InvalidVersionFormat`。复用工作区已有 `semver` 依赖，零新增依赖。

## 7. 判定流程（对齐规范 §5.3 的实现级展开）

```text
assess_compatibility(inspected, env):
  0. env 输入校验（确定性顺序：EmptyModId → DuplicateModId → InvalidVersionFormat →
     ContradictoryMigrationInput，具体见 planning/34 §4 步 0）→ Err(CompatInputError)（非 verdict）
  1. [已在 inspect 完成] 结构+完整性                       → 损坏已在 LoadError 截获
  2. manifest.save_format_version ≤ SUPPORTED             → 否: Blocked/rejected
     （防御层：公开流程中未来格式在 `inspect_save` 的 `verify` 阶段以 `LoadError::Integrity` /
     稳定码 `save.unsupported_format_version` 前置拦截，见 §8「未来版本」行与
     `GK-P4-SAVE-005-OWNER-DECISION-02`）
  3. kernel_api 精确匹配（数值对）+ platform 单向闸门      → 否: Blocked
     （谓词见 §5.6 裁决 B；版本来源边界见 §3.5）
  4. mods 集合比较（缺失/多余；版本仅诊断不作谓词）         → 缺失: Blocked/missing_dependency
  5. 依赖 VersionReq 求值 + kernel_api_requirement 精确匹配 → 不满足: Blocked
  6. world_schema_version 与各 mod schema_version 比较     → 有差异 → 步 7
  7. migration: Available⇒CompatibleWithMigration;
     Unavailable⇒Blocked(schema_mismatch_no_migration)
     （NotRequired 分支已在步 0 拦截：schema 有差异时注入 NotRequired 属输入错误）
  8. SAVE-002 一致性检查结论复用（所有权/未知分区保留确认；已裁决浅落实，见 §5.4）
  9. policy 终裁（§5.5）：Normal ⇒ 管线结果原样输出；
     Strict ⇒ CompatibleWithMigration 改写为 Blocked + rejected + policy_rejected；
     其他 verdict 原样
     + 填充 §13 字段与三布尔（计算基准见 §5.2）→ CompatibilityReport
```

短路规则【契约明示：规范 §5.3 末段】：任一步失败即终止，后续步骤结果不得作为兼容证据；`reason_code` 记录首个失败步。

- **`compat.rs`（纯判定）：** 承载 `assess_compatibility` / `CompatibilityEnv` / `CompatibilityReport` / `CompatibilityVerdict` / `PolicyFlag` / `CompatReasonCode` / `LoadingPolicy` / `MigrationPath`；**零 I/O**、无副作用、可重复（规范 §5.2"判定结果必须可重复"）。
- **单向依赖：** `compat.rs` 消费 `loader.rs` 产出的 `InspectedSave`（类型级依赖）；`loader.rs` **不依赖** `compat.rs`——解析/完整性失败在 `LoadError` 截获，与兼容性判定无耦合。
- **效力标注：** 模块拆分为本次负责人裁决确立的实现组织约束，服务于 DC-10 扫描纪律与纯函数边界；规范未规定模块文件划分。
