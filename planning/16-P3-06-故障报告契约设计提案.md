## 2. 故障报告数据模型与 Schema 边界

### 2.1 `ModFaultReport` 结构（R-4：独立类型）

命名：`ModFaultReport`（Platform 层，与既有 `*Failure` 结构并列；**Kernel 不依赖它**）。

```
ModFaultReport {
  report_version: u32,                 // 报告结构版本（本提案 = 1）
  code: String,                        // 稳定错误码（§3）
  category: FaultCategory,             // §12.1 十四类（§1.3）
  phase: FaultPhase,                   // 阶段（§2.2）
  severity_grade: SeverityGrade,       // L1..L4（§4）
  disposition: Disposition,            // continue/stop/rebuild（§4）
  authoritative: bool,                 // §5 决策表
  retryable: bool,                     // §4
  recovery_advice: RecoveryAdvice,     // §4
  // 上下文（§12.4 全量，命中才填）
  mod_id / mod_version / manifest_version / kernel_api_version /
  platform_version / load_plan_id / instance_id / content_digest /
  tick / scheduler_context / api_id / system_id /
  resource / dependency_context / rollback,
  message: String,                     // 人类可读，非协议字段
}
```

### 2.2 枚举定义（用于 Schema 与实现对齐）

- `FaultCategory`（14）：`manifest` / `package` / `dependency` / `version_conflict` / `permission` / `load` / `initialization` / `api_registration` / `api_invocation` / `wasm_trap` / `resource_limit` / `determinism` / `lifecycle` / `migration`。
  > **决策**：`VersionConflict` 与 `LifecycleError`/`ApiRegistrationError` 等 14 类**一一对应独立枚举值**，不再合并（落实 R-2）。`PlatformError` 的既有 14 个变体与 `FaultCategory` **不是**一一映射（前者是 Rust 错误变体，后者是语义类别），映射见 §3。
- `FaultPhase`：`discovery` / `manifest` / `package` / `resolution` / `lockfile` / `permission` / `compile` / `instantiation` / `registration` / `initialization` / `execution` / `teardown`。
- `SeverityGrade`：`l1_call` / `l2_task` / `l3_mod` / `l4_runtime`。
- `Disposition`：`continue` / `stop` / `rebuild`。
- `RecoveryAdvice`：`none` / `retry_call` / `disable_mod` / `rebuild_instance` / `restore_checkpoint` / `fix_manifest` / `fix_package`。
- `LimitKind`：`fuel_per_call` / `per_tick_fuel` / `memory` / `commands_per_tick` / `events_per_tick` / `tasks` / `api_calls` / `persistent_bytes` / `log_bytes`。

### 2.3 未知字段拒绝规则（R-1）

- 报告 Schema **v1 内 `additionalProperties:false`**：出现任何未在 v1 声明的字段 ⇒ **Schema 校验失败**（与仓库既有 Schema 形态一致）。
- 该规则**只作用于报告的顶层对象与已声明的子对象**；`$defs` 中的每个对象同样 `additionalProperties:false`。
- **边界**：`message` 字段内容不参与未知字段判定（它是文本，允许任意字符但受 `maxLength` 约束）。

### 2.4 版本升级规则（R-1 配套）

| 变更类型 | 是否升 `report_version` | 说明 |
| --- | --- | --- |
| 新增**可选**字段 | **否**（但 v1 内 `additionalProperties:false` ⇒ 消费者拿到含新字段的报告会**校验失败**） | ⇒ **因此新增字段必须同时升 `report_version`**，这是 R-1（拒绝未知字段）与"扩展走版本升级"的**联合约束** |
| 删除字段 | **是**（2 → 破坏性） | — |
| 改字段类型 / 改枚举取值 | **是** | — |
| 改稳定码**含义** | **是**（规范 §12.1 明文禁止随意改义） | — |
| 新增稳定码 | **否**（码集合可见作兼容；含义不冲突即可） | 新码可被 v1 消费者识别为字符串 |
| 改 `message` 文案 | **否**（非协议字段） | — |

> **结论（R-1 的严格读法）**：因 v1 拒绝未知字段，"向后兼容的新增字段"在本仓库**不可行**；任何字段集变化**一律升 `report_version`**。这与仓库"拒绝未知字段"的既有强约束一致——**宁可升版本，不放松校验**。

### 3.1 复用清单（不新增码的类别）

### 3.2 WasmTrap 细分（`wasm_trap` 类别，依据 wasmtime 48.0.5 `Trap`）

| Trap 变体 | 稳定码 | severity | disposition | retryable |

### 3.3 ResourceLimitExceeded 的**两条不同路径**（修订要求 5）

| 触发事实 | 发生时机 | 稳定码 | phase | 机制 |
| --- | --- | --- | --- | --- |
| Fuel 耗尽 | 运行期 | `platform.mod.resource.fuel_exceeded` | execution | `Trap::OutOfFuel` |
| 栈耗尽 | 运行期 | `platform.mod.resource.stack_exceeded` | execution | `Trap::StackOverflow` |
| **静态线性内存上限**（实例化期被 `StoreLimits` 拒绝） | **实例化期** | `platform.mod.resource.memory_limit_exceeded` | **instantiation** | `(memory 2)`=128 KiB > 64 KiB；**非** trap |
| **运行期线性内存越界** | 运行期 | `platform.mod.resource.memory_out_of_bounds` | execution | `Trap::MemoryOutOfBounds` |
| 命令/事件/Task 等配额超限 | 运行期 | `platform.mod.resource.quota_exceeded` | execution | 未来配额实现 |

> **关键区分（可测试）**：实例化期内存限制 vs 运行期内存 OOB **必须**映射到不同 `phase` 与不同码；测试须分别构造（前者用 `memory-limit` 夹具，后者用运行期越界 WAT）。

## 4. 继续/停止/重建决策表（完整版）

对齐任务卡"继续/停止/重建"、§12.2（调用/任务/Mod/运行级）、安全规范 §6.1（L1–L4）。

### 4.1 决策表（14 类逐条）

| 类别 | severity | disposition | 判定条件（何时可继续） | 依据 |
| --- | --- | --- | --- | --- |
| manifest | l1_call | **stop** | 加载前失败，世界未触及 ⇒ 停止该 Mod 加载即可，无需重建 | §12.2 调用级 |
| package | l1_call | **stop** | 同上 | §12.2 调用级 |
| dependency | l1_call | **stop** | 整计划拒绝；世界未触及 | `planning/09` P3-02 |
| version_conflict | l1_call | **stop** | 同上 | P3-02 |
| permission | l1_call | **stop** | 未授权即不注册；世界未触及 | §9.1 deny-by-default |
| load | l2_task | **stop** | 实例化失败，未进入执行 ⇒ 停止该 Mod | §12.1 |
| initialization | l2_task | **stop** | 初始化失败，状态可确认一致 ⇒ 停止该 Mod | §12.2 任务级 |
| api_registration | l2_task | **stop** | 注册前拒绝 | §8.2 |
| api_invocation | l2_task | **stop** | 单次调用失败且未提交 ⇒ 停止当前任务 | §12.2 任务级 |
| wasm_trap | l2_task | **stop** | Kernel 已回滚未提交改动 ⇒ 停止当前 Tick；不能证明一致 ⇒ 升级 rebuild | 安全 §3.3 |
| resource_limit（运行期） | l2_task | **stop** | 同上；Fuel 加预算后可 retry | §10.2 |
| resource_limit（实例化期） | l2_task | **stop** | 未进入执行 | §10.2 |
| determinism | l4_runtime | **rebuild** | 不可确认一致 ⇒ 必须重建 | §13 / §12.2 运行级 |
| lifecycle | l3_mod | **stop** | Mod 不能继续，处理依赖 | §12.2 Mod 级 |
| migration | l4_runtime | **rebuild** | 存档/迁移不安全 ⇒ 重建或恢复检查点 | §14 |

> **硬约束**：决策表**不得**退化为"所有错误统一禁 Mod 后继续"（§12.2 明文禁止）。必须体现 L1/L2/L3/L4 分级。

### 4.2 由决策表派生的不变量（可测试）

- `disposition == continue` **在本阶段无类别默认使用**（当前实现无"可安全继续"路径）；若未来引入，须显式登记。
- `severity ∈ {l3_mod, l4_runtime}` ⇒ `disposition ∈ {stop, rebuild}` 且 `retryable == false`。
- `disposition == rebuild` ⇒ `recovery_advice ∈ {rebuild_instance, restore_checkpoint}`。

## 5. 权威状态四问 → 确定性决策表（R-3：细化，禁止默认继续）

### 5.1 定义

> **权威状态（authoritative state）**：Kernel 在 Tick 边界提交的、构成确定性重放基线的 `World` 状态及其 `state_hash`。

### 5.2 四问（转换为可判定布尔输入）

| 输入 | 含义 | 可判定方式 |
| --- | --- | --- |
| Q1 `touched_committed` | 失败是否发生在**已提交的权威状态被修改之后** | Kernel Contract 事务语义 / 执行阶段 |
| Q2 `uncommitted_rolled_back` | 未提交改动是否已按 Kernel 事务语义回滚/丢弃 | `p1_vertical_slice` 已证 trap 后回滚 |
| Q3 `consistency_provable` | 状态完整性是否**可确认** | 能否证明一致 |

## 6. `ModFaultReport` 与 `SystemError` 的转换边界与依赖方向（R-4）

### 6.1 依赖方向（单向）

```
Kernel (kernel-core)         Platform (platform-core)
───────────────              ────────────────────────
SystemError  ◀── 读取/转换 ──  ModFaultReport
（不感知平台）                  （可引用 SystemError 的字段值，但不被 Kernel 依赖）
```

- **Kernel 不依赖 `ModFaultReport`**（`kernel-core` 的 `Cargo.toml` 不新增对 `platform-core` 的依赖；事实上 `platform-core` 依赖 `kernel-core`，反向依赖会成环 ⇒ 结构上不可能，天然满足）。
- Platform **可**从 `SystemError` **读取** `code`/`system`/`tick`/`source_digest` 填充报告的 `code`/`system_id`/`tick`/`content_digest`，但**不修改** `SystemError` 结构。

### 6.2 转换边界（建议 API）

| 方向 | 建议函数 | 规则 |
| --- | --- | --- |
| `SystemError` → `ModFaultReport` | `ModFaultReport::from_system_error(&SystemError) -> ModFaultReport` | 映射 `code` → 类别（§3）；`system` → `system_id`；`tick` → `tick`；`source_digest` → `content_digest`；`message` 原样进 `message`（非协议） |
| `PlatformError` → `ModFaultReport` | `ModFaultReport::from_platform_error(&PlatformError) -> ModFaultReport` | 按变体映射（§3 表） |
| 不提供的方向 | ~~`ModFaultReport` → `SystemError`~~ | **不提供**（避免平台协议泄漏进 Kernel） |

- **版本解耦**：`report_version`（平台）与 `SystemError::format_version`（Kernel）**互相独立**，各自演进。
- **序列化边界**：报告与 `SystemError` 各自 `serde`；报告不使用 `#[serde(flatten)]` 嵌入 `SystemError`（避免 Kernel 字段成为平台协议一部分）。

## 7. 资源预算报告模型（R-5：数值不冻结）

### 7.1 关系模型

```
BudgetConfig(可配置, 带 config_version) ─┐
                                        ├─► BudgetReport ─► 超限判定 ─► ResourceUse + disposition
ActualUse(实测)                        ─┘
```

- `BudgetConfig`：每资源项的**当前配置值** + `config_version`（对齐安全规范 §5.3）。
- `ActualUse`：实测值（`fuel_consumed` / `memory_bytes` / `commands_this_tick` …）。
- `ResourceUse`（写入报告）：`limit_kind` / `limit_value` / `observed_value` / `config_version` / `exceeded`。

### 7.2 现有默认值——**可配置，非永久契约**

| 常量 | 现值 | 适用范围（现状） | 状态 |
| --- | --- | --- | --- |
| `FUEL_PER_TICK` | `10_000` | 每 Tick 每次执行 | **默认值，可配置；非冻结**（R-5） |
| `MAX_LINEAR_MEMORY_BYTES` | `64 * 1024` | 线性内存静态上限 | **默认值，可配置；非冻结** |
| `MAX_WASM_STACK_BYTES` | `256 * 1024` | Wasm 栈 | **默认值，可配置；非冻结** |

> **R-5 落实**：报告模型**只描述**"配置值/实测值/是否超限"，**不把上述数值写成契约**；Safe/Perf 规范 §5.4 明示示例值"不是最终冻结值"，且 §17.5 禁止"用文档完整代替功能完成"。本阶段**不做**任何性能达标声明。
