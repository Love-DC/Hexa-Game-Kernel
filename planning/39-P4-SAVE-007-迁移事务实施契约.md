# P4-SAVE-007 迁移事务实施契约

- **文档编号：** planning/39
- **状态：** 按负责人委托采纳默认安全方案，实施契约
- **上游：** Save §8–§10/§15；`planning/22`；`planning/30`；SAVE-006 契约 `planning/37` 与报告 `planning/38`

## 1. 范围和边界

在 SAVE-006 计划上执行一个受控迁移事务：校验输入、建立可验证恢复副本、逐步调用受信任的装配层 `MigrationRunner`、组装新 Manifest/分区、验证候选存档、写提交日志并原子替换正式目标；支持根据日志和摘要恢复未完成事务。Runner 只接收当前步骤按描述符 scope 授权的只读输入，并返回显式输出，不拿到 `SaveLayout` 或可变 World 引用。save-manager 不加载/执行 Wasm、不增加 platform-core 依赖；迁移运行 ABI 及实际 platform-core 沙箱 adapter 仍须后续补齐，本地 fake runner 测试不能冒充 ABI 验收。

新增 `transaction.rs`、`migration_transaction_contract.rs`；不得改 Kernel、SAVE-005 类型、SAVE-006 语义或 `Cargo.toml`。DC-10 扩展为 `writer.rs`（正常保存）、`loader.rs`（只读加载）、`transaction.rs`（SAVE-007 事务/恢复）三个具名 I/O 模块；除此之外生产 Rust 模块仍禁止文件/网络/进程/时钟访问。transaction.rs 仅允许读取进程 ID 用于 sidecar 唯一命名；禁止进程创建、网络、时钟及 unsafe。此项是对 `planning/30` §13 的 SAVE-007 专项增补，不改变 writer 的职责。

## 2. 输入与执行接口

- 入口接收目标路径、已通过 SAVE-005 检查的 `InspectedSave`、SAVE-006 `MigrationPlan`、新的完整目标 Manifest、系统 ID、调用方提供的时间戳及 `MigrationRunner`。
- 必须先验证 `plan.save_id`、`plan.source_root_hash` 与原档 Manifest 一致，目标 Manifest save_id 不变，目标数据 Schema 与计划最后一步一致；不一致返回结构化输入错误、不得调用 Runner。
- `MigrationRunner::run(&PlannedMigration, MigrationInput) -> Result<MigrationOutput, RunnerError>` 是可信装配边界。`MigrationInput` 只给该步 `input_scope` 声明的数据不可变字节；无权访问磁盘、网络、时钟或进程的要求由未来 sandbox adapter 执行。
- 输出只能包含声明在 `output_scope` 的分区；不得改变其他分区。World 数据通过 save-manager 托管，Mod 代码不可取得 World 写引用。每步输入/输出 schema 必须与描述符 `from_schema`/`to_schema` 相符，步骤按计划顺序执行。
- Runner 失败保留稳定步骤号、migrator ID 与错误类别；原档不变，恢复副本保留，工作候选可按事务状态清理。
- 提交候选前必须要求调用方提供 `MigrationCandidateValidator`，对完整候选 Manifest/Layout 执行世界不变量和跨 Mod 引用验证；无默认放行实现。SAVE-010 提供引用验证；缺少验证器或验证失败则 fail closed。

## 3. 文件与日志协议

- 目标同目录使用确定性 sidecar 名：恢复副本、工作候选、单一活动事务日志、日志原子更新临时文件；路径均从目标文件名和经过校验的事务 ID 构造，不接受日志中任意路径越出目标目录。不得 glob 清理。
- 同一目标只允许一个活动事务：同目录创建固定的隐藏 `.migration-lock` 协调文件并获取标准库文件排他锁（锁随进程句柄关闭自动释放）；该空协调文件在迁移后保留，禁止手工/清理任务删除。活动日志再以 `create_new` 建立；已有日志意味着必须先恢复/诊断，不能并发覆盖。所有 migrate/recover 调用都先获取同一锁，恢复不能干扰仍运行的 Runner。
- 日志最少记录协议版本、事务 ID、原 save_id/root_hash、候选 root_hash（候选就绪后）、计划摘要、当前阶段、最近完成步骤和失败稳定码/Runner 子码/步骤/迁移器 ID（适用时）。目标路径由调用 `migrate/recover` 时显式提供；恢复副本与 work 路径由已校验的事务 ID 从目标目录推导，不从日志读取任意文件路径。每条记录以 append-only JSONL 写入并 `sync_all`；不承诺掉电耐久。
- 阶段：`Started` → `BackedUp` → `Executing` → `CandidateReady` → `CommitStarted` → `Committed`；可在提交前转为 `Failed` 并记录稳定错误码与步骤诊断。阶段单调前进；日志未知版本/非法 ID/不合法跳转必须 fail closed。
- 恢复副本必须在第一次调用 Runner 前创建、读回并经 `inspect_save` 完整验证；副本内源档字节/根哈希与计划相符。备份不可被事务清理流程删除。
- 候选通过容器结构、Manifest、完整性和分区一致性检查后才写 `CandidateReady`；写 `CommitStarted` 后 rename work→target；rename 返回成功后写 `Committed`。崩溃后以日志阶段与 target/work/backup 的 `save_id + root_hash` 识别实际状态，不重复调用 Runner。

## 4. 恢复规则

恢复入口只消费活动日志指向的确切路径，并先验证每个候选文件：

1. target root 等于候选 root：提交已完成，确认状态并完成日志收尾，不再次迁移。
2. target root 等于原 root：原档仍完整；若候选完整且日志处于 `CandidateReady/CommitStarted`，可完成已准备好的 rename；否则中止并保留原档。
3. target 无效/不存在/既非原 root 也非候选 root：只在恢复副本验证通过后，将该副本经同目录恢复临时文件验证后替换 target；替换后再次 `inspect_save`。备份损坏/恢复失败均不删除备份，也不谎报成功。
4. 未知/无效日志、路径越界或无法确定 target 状态：停止写入，保留日志和所有恢复材料，返回人工诊断错误。

日志清理只在 target 已验证为候选或原档、恢复副本仍可恢复且状态明确时执行。SAVE-008 再扩展备份保留策略、历史备份/恢复用户流程及故障注入工具；本包不清理既有恢复副本。

## 5. 验收

契约测试至少覆盖：输入 hash/id/schema 拒绝且 Runner 未调用；scope 输入/输出隔离；多步顺序和版本校验；Runner 每一步失败均保留原档；候选生成/验证失败保留原档；commit 前后崩溃恢复矩阵；日志截断/未知版本/非法状态/路径越界 fail closed；日志所指备份损坏、恢复失败时不删除备份；目标已提交时恢复不重复执行 Runner；活动日志排他；恢复后再次完整性验证；Windows 与 Linux CI 实际 rename 行为。所有错误保留事务阶段与稳定码。

完成 SAVE-007 不能关闭 GAP-24(c)（迁移执行确定性观测）或 GAP-25（platform 故障报告 adapter）。SAVE-008 要提供并运行真实故障注入矩阵；SAVE-012 要纳入最终全平台验收。门禁沿用 `planning/22` §六。
