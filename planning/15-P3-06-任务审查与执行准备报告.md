## 1. GK-P3-06 的任务目标与范围

### 1.1 任务卡原文（`planning/09:60-65`）

- **范围：** Manifest/Resolver/权限/Runtime/Mod 执行失败以及 Wasm 的 Fuel/Memory 限制报告。
- **实施：** 统一稳定错误码、阶段、Mod ID、内容摘要、Tick（若已进入模拟）、可重试性及恢复建议；避免把权威模拟失败归类成可忽略的非权威错误。
- **测试：** 导入拒绝、燃料超限、内存超限、Guest Trap、非法 Host 输出及恢复重建；报告自身有版本和 Schema 校验。
- **验收：** 每类错误明确"继续/停止/重建"；日志诊断可复现，错误文本不作为协议字段。

### 1.2 目标提炼

GK-P3-06 交付的是一个**统一的、机器可读的故障报告（fault report）模型 + 资源预算报告**，覆盖从 Manifest → Resolver → 权限 → Runtime → Mod 执行的全链路失败，并对 Wasm 的 Fuel / Memory 超限给出可诊断结果。核心不是"新增更多错误"，而是把**已有的分散失败点收敛为统一报告契约**，并为每类失败明确"继续 / 停止 / 重建"处置等级，同时**禁止把权威模拟失败降级为可忽略错误**。

### 1.3 与相邻阶段的关系

- 上游：`P3-05 → P3-06`（任务卡 §依赖与顺序，`planning/09:74`）。P3-06 是 P3-05 的**唯一直接后继**，全部汇入 `P3-07`。
- P3-06 **不扩展**权限面、Host API 数量、Resolver 语义或 Kernel 契约，**不实现**热重载、WASI、网络/文件 API（任务卡 §本阶段明确不做）。
- 任务卡已明示：`DependencyResolutionFailure` 的**持久报告 Schema 属 GK-P3-06**（`planning/09:108`），即 P3-06 需为已有结构化失败载荷补正式报告 Schema。

## 4. 主要风险及阻塞项

### 4.1 阻塞项（硬/软）

| 编号 | 风险/阻塞 | 级别 | 说明 |
| --- | --- | --- | --- |
| B-1 | **Fuel 超限与 Guest Trap 在 Wasmtime 侧同源，当前均被折叠为 `platform.mod.execution_failed`** | 软阻塞 | 现有 `WasmSystem::execute` 对 `on_tick.call(...)` 的任意 `Err` 都用 `ExecutionFailed`（`lib.rs:1614-1616`）。任务卡要求区分"燃料超限 / 内存超限 / Guest Trap"。需在 P3-06 中**按 Wasmtime Trap 具体类型细分**，否则"每类错误明确继续/停止/重建"无法达成。 |
| B-2 | **报告 Schema 的字段集未由任务卡/规范冻结** | 软阻塞 | 规范 §12.4 给出**至少 13 项**诊断字段（运行实例 ID、Mod ID/版本、Manifest 版本、Kernel API 版本、平台版本、加载计划标识、错误代码、错误阶段、Tick/调度上下文、相关 API/System/任务标识、资源使用、依赖上下文、是否回滚/恢复）。任务卡只列了子集（错误码、阶段、Mod ID、内容摘要、Tick、可重试性、恢复建议）。**两者必须对齐**，否则报告契约不完整。见 §5 C-1。 |
| B-3 | **"权威模拟失败 vs 非权威错误"的分类边界未在任何文档给出判定标准** | 软阻塞 | 任务卡要求"避免把权威模拟失败归类成可忽略的非权威错误"，但未定义哪些失败属"权威"。需澄清（见 §5 C-2），否则无法设计 `authoritative` 字段语义。 |
| B-4 | **Trap → 错误码的映射表未冻结** | 软阻塞 | 需明确 `TrapCode`（如 `OutOfFuel`/`MemoryOutOfBounds`/`Unreachable`/`IntegerOverflow`…）到稳定子码的映射，且该映射必须可版本化、可测试。属实现细节，但需在开始前确认映射原则。 |

> 以上均为**软阻塞**（可通过澄清 + 设计解决），**无不可绕过的硬阻塞**。

### 4.2 其他风险

- **R-1 报告膨胀**：把全链路失败统一到一个报告类型，可能造成单一巨型结构体；需权衡"统一码 + 可选上下文字段"vs"多子类型"。任务卡未指定实现形态。
- **R-2 与 `SystemError` 的重复**：Kernel 已有 `SystemError`（含 `format_version`），Platform 若另造一套报告会形成双轨。需明确二者关系（Platform 报告是否包裹/扩展 `SystemError`）。
- **R-3 回归面广**：Runtime 错误分类细化会触碰 `WasmSystem::execute`，属核心执行路径，必须重跑全部门禁与 P1 集成测试（`p1_vertical_slice` 已断言 `platform.mod.execution_failed`，**细化后该断言可能需更新**——这属于既有测试的合法演进，但需显式披露，不得为通过而删测试）。
- **R-4 规范 v1 未冻结数值**：安全性能规范 §5.4 明确示例配额"不是最终冻结数值"，§10.1 要求默认值"必须在性能、安全规范中正式冻结"。P3-06 **不应**擅自冻结/声明达到某性能目标（§5.4 末句 + 规范 §17.5「不得用文档完整代替功能完成」）。
- **R-5 与 G-1/G-2/G-3/G-6 缺口的关系**：P3-05 遗留的规范缺口（`Failed` 恢复、`Unloaded` 重载、`Disabled` 语义、全局一致性）**不属于** P3-06 范围，但 P3-06 的"恢复建议/重建"措辞不得与之冲突（尤其不得暗示支持热重载或原地恢复）。

## 5. 建议的实现顺序（供授权后参考）

1. **冻结报告契约**：先定义统一故障报告结构（版本号 + 稳定码 + 阶段 + Mod ID + 内容摘要 + Tick + 可重试性 + 处置等级 + 恢复建议 + §12.4 诊断字段）+ 报告 Schema，并**先冻结**再写实现（沿用 P3-04/P3-05 的"先冻结 descriptor / 状态转换"纪律，见任务卡 §依赖与顺序末句）。
2. **建立错误码映射表**：把现有全链路失败点（§3.3）映射到统一报告；新增最少必要稳定码（例如"资源超限"需独立码，不得复用 `execution_failed`）。
3. **Runtime 细分**：在 `WasmSystem::execute` 按 Wasmtime Trap 类型区分 Fuel 超限 / Memory 超限 / Guest Trap（对应 B-1、B-4）；保持对 Kernel 契约的只读依赖。
4. **授权失败链路**：为每个报告标注"继续 / 停止 / 重建"处置等级（对齐 §12.2 调用级/任务级/Mod 级/运行级；安全性能规范 §6.1 的 L1–L4）。
5. **报告 Schema 校验 + 版本**：报告自身通过 Schema 校验，带 `format_version`（任务卡 + §12.1）。
6. **测试**：覆盖任务卡四类用例——导入拒绝、燃料超限、内存超限、Guest Trap、非法 Host 输出、恢复重建；并新增"报告 Schema 自校验"测试。
7. **门禁**：`cargo fmt --all -- --check`、`cargo clippy --locked --workspace --all-targets -- -D warnings`、`cargo test --locked --workspace`、`cargo run --locked -p game-platform -- demo`（demo 须保持 `verified=true`）。
