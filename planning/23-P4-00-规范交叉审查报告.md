## 四、问题清单（含证据、影响、最小修正建议）

### F-1 架构目录布局与实现不一致（save-manager 落位）
- **证据：** `Project Architecture v1.0.md` §2（L113-188）规定目录为 `kernel/kernel-core`、`platform/{mod-manager,mod-runtime,api-registry,save-manager,...}`；实际仓库为扁平 `crates/kernel-core` + `crates/platform-core`（`ls crates`）。Architecture §2（L190-192）允许"目录与 workspace 成员按契约增量加入"。
- **影响：** P4 新建存档载体时，"`crates/save-manager`（沿用实际扁平约定）"与"`platform/save-manager`（沿用架构树）"两种落位均有依据，需明确。
- **最小修正建议：** 由负责人裁定落位（见 GK-P4-01 卡 Q1）；本报告建议**沿用实际扁平约定 `crates/save-manager`**，并在决定记录中注明与架构 §2 目录树的差异。**不擅自修改架构规范。**

### F-2 `kernel-api` 独立 crate 缺失（Kernel 公共接口载体）
- **证据：** Architecture §3.2（L220）定义 `kernel/kernel-api` crate；实际无该 crate，`Kernel Contract` §12（L228-242）要求的公共接口由 `kernel-core` 提供；`platform-core/Cargo.toml:10` 直接 `kernel-core = { path = "../kernel-core" }`。
- **影响：** save-manager 消费 Kernel 公共接口时的依赖目标应为 `kernel-core`（当前唯一 kernel crate），而非架构树中的 `kernel-api`。
- **最小修正建议：** 在决定记录中确认 `save-manager → kernel-core`（Architecture §4.2 L448 已禁 `kernel-core → save-manager`，反向允许）；若后续拆分 `kernel-api`，再调整。

### F-3 依赖边界自动检查缺失
- **证据：** Architecture §4.4（L463-475）："The project MUST automate dependency-boundary checks……A written rule without an automated check is insufficient"；完整项目规范 §2.2（L174）同旨。实际无 `deny.toml`、无 `tests/architecture/`、无依赖方向检查代码（`ls -a`/`find`）。
- **影响：** 新增 crate（save-manager）增加环依赖/越界依赖风险，而当前无自动化护栏；P4 验收不得假定该检查已存在。
- **最小修正建议：** 登记为待补齐项；建议在 P4 内（或独立小任务）增加**最小依赖方向检查**（基于 `cargo metadata` 断言：`kernel-core` 不依赖任何平台 crate、无环）。**本任务不实现。**

### F-4 版本模型跨规范不一致（影响 SAVE-001 核心交付）
- **证据：**
  - Save 规范 §3.4（L196-209）：**6 项**——Save Format / World Schema / Mod Schema / **Platform Version** / Kernel API Version / Mod Version。
  - 完整项目规范 §6.2（L498-508）：**5 项**——Save Format / **Kernel State Schema** / Mod Data Schema / **Game Definition Version** / **API Version**。
  - Architecture §7（L602-610）：**7 项**——save file format / world-state schema / Mod-owned persistent schema / Mod code version / Kernel API version / **Runtime version** / **Migration implementation**。
- **影响：** "版本分离"是 `SAVE-001` 的核心交付；三份规范给出不同集合（Platform vs Game Definition vs Runtime；World Schema vs Kernel State Schema；Mod Version vs Mod code version）。
- **最小修正建议：** 建议以 **Save 规范 §3.4 为存档域权威集合**（`SAVE-001` 据此实现）；对**完整项目规范 §6.2 的 `Game Definition Version`** 与 **Architecture §7 的 `Runtime Version`** 作为"候选追加字段"登记，由负责人裁定纳入或显式延后。**不擅自合并。**

### F-5 存档必需元数据缺 `Game Definition` 字段
- **证据：** Save 规范 §3.2（L142-157）必需元数据**未列** Game Definition；§3.3 示例（L165-191）亦无该字段。完整项目规范 §6.1（L494："存档必须能够说明自己由什么游戏定义……产生"）、§6.3（L515："Game Definition 标识与版本"）、L140（"不得默认不同游戏定义之间可以共享存档"）要求记录之。
- **影响：** `SAVE-001` 的 Manifest 模型/ Schema 可能不满足完整项目规范 §6.1/§6.3；跨 Game Definition 存档判定的基础字段缺失。
- **最小修正建议：** 建议在 `SAVE-001` Manifest 中**预留 `game_definition {id, version}` 字段**（或显式声明本阶段延后并记录理由）；由负责人裁定。

### F-6 Save 规范内部：§3.2 必需项 vs §3.3 示例字段不一致
- **证据：** §3.2（L156）要求记录"与确定性恢复相关的运行配置"；但 §3.3 示例 Manifest（L165-191）**未包含**该字段；GK-P4-01 卡 §五.1 的字段清单亦未包含。
- **影响：** `SAVE-001` 字段集合存在歧义（示例缺项 vs 必需项）。
- **最小修正建议：** 建议 `SAVE-001` **纳入"确定性恢复运行配置"字段**（`simulation_config` 或等价），或显式延后并记录理由；由负责人裁定。**不改规范。**

### F-7 兼容性结论分类跨规范不一致（影响 SAVE-005）
- **证据：**
  - Save 规范 §5.1（L266-294）：**4 类**——`Compatible` / `CompatibleWithMigration` / `Blocked` / `Corrupted`。
  - 完整项目规范 §6.8（L581-595）：**7 类**——可直接加载 / 需要迁移 / 需要用户确认 / 需要补充依赖 / 存在功能降级 / 不建议加载 / 必须拒绝加载。
- **影响：** `SAVE-005`（兼容性判定）的分类枚举若只按 Save 规范 4 类，可能无法表达 §6.8 的"需用户确认/需补充依赖/功能降级/不建议加载"；反之若按 7 类，与 §5.1 的机器可读码不对齐。
- **最小修正建议：** 建议将 Save 规范 §5.1 的 **4 个结果码作为机器级分类（machine-level）**，完整项目规范 §6.8 的 **7 项作为用户/策略级细化（granular）**，并建立映射表；由负责人在 `SAVE-005` 前裁定。**不擅自合并或改码。**

### F-8 P4"重放"范围未显式界定
- **证据：** roadmap P4 主要交付含"黄金存档与输入重放"（`planning/03:14`）；Kernel Contract §10（L209）"Cross-version replay is a separate capability; save compatibility does not imply replay compatibility"、§14（L268）跨平台逐位确定性在 v1 之外；完整项目规范 L802"存档兼容不代表旧输入日志可以跨版本重放"。
- **影响：** P4 的"重放"必须界定为**同版本/同配置下的回归重放（黄金档 + 输入重放定位差异）**，不含跨版本/跨平台重放；否则会与 Kernel Contract 冲突。
- **最小修正建议：** 在 GK-P4-01 卡中**增补"重放边界"条款**：P4 仅承诺同一确定性边界内的重放回归；跨版本重放属独立能力，不在 P4 范围。**不改规范。**

### F-9 `GAP-24`/`GAP-25` 落地包映射建议复核
- **证据：** `planning/02:57`（GAP-24 = `DeterminismViolation` 检测）、`planning/02:58`（GAP-25 = `MigrationError` 检测）；Save 规范 §8.4（L515-525 迁移纯度/确定性）、§9.3（L583-593 迁移失败处理）；GK-P4-01 卡 §九 将 GAP-24→`SAVE-006`、GAP-25→`SAVE-005`。
- **影响：** `MigrationError` 语义为"迁移执行失败"，更贴近 `SAVE-006`（迁移器/链）/`SAVE-007`（临时副本与原子提交 + 失败处理）；`DeterminismViolation` 贴近 `SAVE-006`（迁移纯度）。当前 25→`SAVE-005` 的映射可能偏窄。
- **最小修正建议：** 建议将 **GAP-25 → `SAVE-006`/`SAVE-007`**、**GAP-24 → `SAVE-006`**，并在 `SAVE-012` 收尾验收；由负责人确认。

### 3. `save-manager` 的架构位置与依赖边界
- **位置：** Architecture §3.6（L288-303）定义 `platform/save-manager`，职责含"Save file reading/writing、Snapshot coordination、Serialization、Metadata、Schema versioning、Migration orchestration、Backup/recovery、Integrity verification"。完整项目规范 §2.1B（L131）将"存档兼容性判断与迁移协调"列为 Platform 职责。
- **依赖边界：** Architecture §4.2（L446-450）**禁止** `kernel-core → save-manager`；反向（`save-manager → kernel-core`）允许。§7（L600-618）明确 Save 兼容性属平台层。
- **结论：** 存档载体**应位于平台层、依赖 kernel（公共接口）而非被 kernel 依赖**——与 GK-P4-01 卡 §五"不得放入 kernel-core"一致。**落位命名见 F-1；Kernel 公共接口载体见 F-2。**

### 4. `SAVE-001` 接口、Schema 与后续迁移需求一致性
- **接口/Schema：** 卡 §五 字段集对齐 Save 规范 §3.2/§3.3/§3.4，方向正确；但存在 **F-5**（缺 Game Definition）、**F-6**（缺确定性运行配置）、**F-4**（版本集合）三处需先裁定。
- **与后续迁移需求：** `SAVE-001` 明确"不做 I/O、不生成 `root_hash`（属 SAVE-003）、不涉及迁移执行"，与 `SAVE-003`/`SAVE-005~008` 边界清晰、无重叠。§3.2"如果联机或重放需要额外元数据，由对应规范补充"——重放额外元数据**延后**，与 F-8 边界一致。
- **结论：** 接口方向可用，**Schema 冻结前须解决 F-4/F-5/F-6**。

### 5. P4 进入条件是否满足
- roadmap P4 门槛两项：① 专项规范已补齐 ✅（Save 规范已入库）；② 与总规范/Kernel/Mod 交叉审查 → **本次完成**。
