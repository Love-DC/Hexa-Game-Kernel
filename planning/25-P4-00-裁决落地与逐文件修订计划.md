## 二、F-4 最终字段语义（版本模型，方向 D1）

### 2.1 结论

以 **Save 规范 §3.4 的 6 项**为**存档域权威版本集合**；`SAVE-001` Manifest 的版本字段**据此命名与实现**；其余规范的同义/近义项以**映射表**对齐，**不新增字段**（跨域项除外，见 2.4）。

### 2.2 最终字段语义（`SAVE-001` Manifest 版本相关字段）

| 字段（canonical） | 语义 | 来源（权威） | 类型/取值 |
|---|---|---|---|
| `save_format_version` | 存档容器与元数据格式版本 | Save §3.4 Save Format Version | SemVer-ish 字符串（示例 `"1.0"`） |
| `world_schema_version` | 世界数据结构版本 | Save §3.4 World Schema Version | 字符串 |
| `mods[].schema_version` | 单个 Mod 的持久化数据结构版本 | Save §3.4 Mod Schema Version | 字符串 |
| `platform_version` | 平台发布版本 | Save §3.4 Platform Version | SemVer |
| `kernel_api_version` | 内核接口合同版本 | Save §3.4 Kernel API Version | 字符串（示例 `"1.0"`） |
| `mods[].version` | Mod 自身发布版本 | Save §3.4 Mod Version | SemVer |

> 以上 6 项即 `SAVE-001` 的**版本集合**（与 §3.4 逐项对应）；`game_definition`（§四）为**标识元数据字段**，**不并入**本集合。

### 2.3 跨规范同义映射表（最终）

| Save §3.4（权威） | 完整项目规范 §6.2 | Project Architecture §7 | 处置 |
|---|---|---|---|
| Save Format Version | Save Format Version | save file format | **同义**（§3.4 名为准） |
| World Schema Version | Kernel State Schema Version | world-state schema | **同义** → 统一用 `world_schema_version` |
| Mod Schema Version | Mod Data Schema Version | Mod-owned persistent schema | **同义** → `mods[].schema_version` |
| Platform Version | —（§6.2 无） | Runtime version | **待 Q-F4-a**：合并为 `platform_version` 或并列 `runtime_version` |
| Kernel API Version | API Version | Kernel API version | **同义** → `kernel_api_version` |
| Mod Version | —（§6.2 无） | Mod code version | **同义** → `mods[].version` |
| —（不在 §3.4） | Game Definition Version | — | **不并入** → 作为 §四 元数据字段 `game_definition.version` |
| —（不在 §3.4） | — | Migration implementation | **非存档元数据** → 归 `SAVE-006` 迁移实现标识（不写入 Manifest） |

### 2.4 失败处理（F-4）

- 版本字段**缺失/类型非法/空串** → `save.missing_field` / `save.invalid_version`（稳定码 + JSON Pointer）。
- **高于当前支持格式版本**的存档 → `SAVE-001` 仅做**模型层拒绝**（稳定码 `save.unsupported_format_version`），**不涉 I/O**（对齐 Save §12.2；实际写入保护在 `SAVE-004` 起）。
- **不比较跨域版本**：`SAVE-001` 只承载字段与自洽校验，**不做**平台/Kernel 兼容比较（属 `SAVE-005`）。

### 2.5 验收条件（F-4）

1. Manifest 版本字段与 §3.4 六项**逐项对应**、命名冻结。
2. 映射表（2.3）归档入**决定记录**（非规范正文），并注明 `Platform/Runtime` 的最终裁定（Q-F4-a）。
3. 非法/缺失/未来版本均被**机器可读稳定码**拒绝，含字段路径。

## 三、F-5 最终字段语义（`game_definition`，方向 E1）

### 3.1 结论

`SAVE-001` Manifest **纳入必填** `game_definition`，结构：

```
"game_definition": { "id": "<stable-id>", "version": "<semver>" }
```

### 3.2 语义与来源

- 满足**完整项目规范 §6.1（L494）**"存档必须能够说明自己由什么游戏定义……产生"、**§6.3（L515）**"Game Definition 标识与版本"、**L140**"不得默认不同游戏定义之间可以共享存档"。
- 属**元数据字段**，与 §二 的版本集合**分离**。

### 3.3 失败处理（F-5）

- `game_definition` 缺失 → `save.missing_field`（路径 `/game_definition`）。
- `id` 格式非法（非稳定标识） → `save.invalid_game_definition`。
- `version` 非 SemVer → `save.invalid_version`。
- 跨 Game Definition 兼容判定在 `SAVE-005` 消费该字段（**不在** `SAVE-001` 判定）。

### 3.4 验收条件（F-5）

1. Schema `required` 含 `game_definition`，且 `id`/`version` 均必填。
2. 非法/缺失被稳定码拒绝。
3. 字段作为 `SAVE-005` 兼容判定输入之一（接口预留）。

### 3.5 未决子项

- **Q-F5-a：** 是否允许早期单 Game Definition 场景 `null`（退化为方案 E3）？**建议：必填，不允许 `null`**（与 L140 隔离原则一致）；如需兼容早期场景，另行裁定。

## 四、F-6 最终字段语义（确定性运行配置，方向 F1）

### 4.1 结论

`SAVE-001` **定义并纳入** `simulation_config` 字段；**本轮允许空/占位**，真实值由 `SAVE-004`（一致快照与正常保存）填充。

### 4.2 语义与来源

- Save 规范 **§3.2（L156）**"与确定性恢复相关的运行配置"为**必需元数据**；§3.3 示例（L165-191）缺该字段（F-6 冲突源）。
- 命名沿**完整项目规范 §6.3（L523）**"必要的模拟配置"与 §6.1（L494）"必要的模拟配置"，取 **`simulation_config`**。

### 4.3 失败处理（F-6）

- 字段**类型非法** → `save.invalid_simulation_config`。
- `SAVE-001` 阶段 `simulation_config` 为**空/占位合法**（因值为 `SAVE-004` 职责）；**加载期**若必需而缺失 → 由 `SAVE-005` 判定（不属 `SAVE-001`）。

### 4.4 验收条件（F-6）

1. Schema 定义 `simulation_config` 结构（可为空对象/占位）。
2. 类型非法被稳定码拒绝。
3. `SAVE-001` **不填真实值**（纯内存、无 I/O）；与 `SAVE-004` 的填充接口在 `SAVE-001` 冻结。

### 4.5 未决子项

## 五、F-7 最终分类与映射（方向 G1）

### 5.1 结论

**双层分类：** 机器级 **4 码**（Save §5.1 权威，机器可读）+ 用户/策略级 **7 类**（完整 §6.8）+ **映射表**；`SAVE-005` 输出 = 机器码 + 策略级细化标记 + 原因码（§13）。

### 5.2 最终映射表（提案；`SAVE-005` 冻结前待批）

| 完整 §6.8（用户/策略级） | Save §5.1（机器级） | 细化标记 | 原因码示例（§13） | 需备份 | 可能丢数据 | 允许自动继续 |
|---|---|---|---|---|---|---|
| 可直接加载 | `Compatible` | — | — | 否 | 否 | 是 |
| 需要迁移 | `CompatibleWithMigration` | — | — | 是 | 可能 | 获授权后 |
| 需要用户确认 | `CompatibleWithMigration` | `requires_user_confirmation` | — | 是 | 可能 | **否（待确认）** |
| 需要补充依赖 | `Blocked` | `missing_dependency` | `SAVE_MOD_REQUIRED_MISSING` | 否 | 否 | 否 |
| 存在功能降级 | `Compatible` | `degraded` | （warning 码） | 是 | 否 | 是（附警告） |
| 不建议加载 | `Blocked` | `discouraged` | — | 是 | 可能 | 否 |
| 必须拒绝加载 | `Blocked` / `Corrupted` | `rejected` | — | 视情况 | 视情况 | 否 |

> `Blocked`／`Corrupted` 的区分以 **§5.3 判定优先级**为准（结构/完整性失败 → `Corrupted`）；`Blocked` 不代表损坏（§5.1 L292）。

### 5.3 失败处理与优先级（F-7）

- 结果必须**可重复**且含**机器可读原因码**（§5.2 L311）。
- 第 7 步"查找可用迁移路径"与 `SAVE-006` 存在**接口耦合**：**契约由 `SAVE-005` 定义、实现由 `SAVE-006` 提供**（依赖细化，非冲突；见 `planning/23` §五.1）。

2. 映射表（5.2）**纳入 `SAVE-005` 契约测试**（Q-F7-a 待确认后冻结）。
3. `§13` 要求的字段（结论/代码/Mod ID/当前版本/记录版本/失败条件/处理选项/是否需要备份/是否可能丢数据/是否允许自动继续）齐备。

## 六、F-1/F-2/F-3/F-8/F-9 修改范围与实际工程结构核对

### 6.1 F-1 save-manager 落位

- **实际工程结构（核实）：** `ls crates` = `kernel-core` + `platform-core`（**扁平**）；根 `Cargo.toml` `members` 仅此两项。
- **规范：** Architecture §2（L113-188）为**嵌套目录树**（`platform/save-manager/` L155、`kernel/kernel-api/` L146）；§2（L190-192）允许"目录与 workspace 成员按契约增量加入"。
- **结论/建议：** 采用**实际扁平约定 `crates/save-manager`**；**不修改** Architecture 正文；在**决定记录**中注明与 §2 目录树的差异；`SAVE-001` 建 crate 时在根 `Cargo.toml` 增 `members` 一项。

### 6.2 F-2 Kernel 公共接口载体

- **实际工程结构（核实）：** **无** `kernel-api` crate；`platform-core/Cargo.toml:10` = `kernel-core = { path = "../kernel-core" }`。
- **规范：** Architecture §3.2（L220）定义 `kernel/kernel-api`；§4.2（L448）**禁止** `kernel-core → save-manager`（反向允许）；§7（L600）Save 兼容属平台层。
- **结论/建议：** 确认 **`save-manager → kernel-core`**（当前唯一 kernel crate）；**不改**规范；若后续拆分 `kernel-api` 再调整。

### 6.3 F-3 依赖边界自动检查缺失

- **实际工程结构（核实）：** **无** `deny.toml`/`audit`；**无** `tests/`（根）；**无** `tests/architecture/`；**无**依赖方向检查代码。
- **规范：** Architecture §4.4（L463-475）"MUST automate dependency-boundary checks"；完整项目规范 §2.2（L174）同旨。
- **结论/建议：** 登记为**待补齐项**；建议在 P4 内（或独立小任务）增加**最小依赖方向检查**（基于 `cargo metadata` 断言：`kernel-core` 不依赖任何平台 crate；无环）。**本任务不实现**；`SAVE-001` 验收**不得假定该检查已存在**。

### 6.4 F-8 "重放"边界

- **规范：** Kernel Contract §10（L209）"Cross-version replay is a separate capability; save compatibility does not imply replay compatibility"；§14（L268）跨平台逐位确定性在 v1 之外；完整项目规范（L802）"存档兼容不代表旧输入日志可以跨版本重放"。
- **结论/建议：** 在 `planning/22` **增补"重放边界"条款**——P4 仅承诺**同确定性边界内的回归重放**（黄金档 + 输入重放差异定位）；**跨版本/跨平台重放不在 P4 范围**；**不改**规范。

### 6.5 F-9 GAP-24/25 落地包映射

- **现有映射（核实）：** `planning/22` L84 = `SAVE-005`（含 GAP-25）／L85 = `SAVE-006`（含 GAP-24）／L168 = GAP-24→`SAVE-006`、GAP-25→`SAVE-005`；`planning/02` L57 = GAP-24（`DeterminismViolation`，占位）／L58 = GAP-25（`MigrationError`，占位）。
- **结论/建议：** 修订为 **GAP-25 → `SAVE-006`/`SAVE-007`**（迁移执行与事务失败）、**GAP-24 → `SAVE-006`**（迁移纯度/确定性），二者在 `SAVE-012` 收尾验收；同步修订 `planning/22` §四表注与 §九。**不改** `planning/02` 的 GAP 现状（另见 §九 修订计划）。
