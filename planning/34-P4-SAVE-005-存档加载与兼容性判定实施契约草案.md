## 0. 负责人裁决落实记录

> 以下六项由 `GK-P4-SAVE-005-OWNER-APPROVAL-01`（2026-10-19）正式批准；本契约据此定稿。前两批裁决（DECISION-01 / DECISION-05）见 `planning/33` 文档头。

1. **B-1 Mod 自身 `version` 兼容规则：** 批准方案③——Mod `version` **不作**存档兼容性判定条件，仅用于诊断信息。保留 `mod_version_incompatible` 原因码，但当前规则下零触发。
2. **B-2 `kernel_api_requirement` 兼容规则：** 批准精确匹配——Mod 声明的 `kernel_api_requirement` 与当前内核 API 版本解析为 `SaveFormatVersion` 数值对后精确匹配，不匹配 ⇒ `Blocked + mod_api_incompatible`。仅在 `compat.rs` 内实现，不修改 `platform-core`。
3. **B-3 结构化输入错误接口：** 批准 `Result<CompatibilityReport, CompatInputError>`。四变体：`DuplicateModId`、`InvalidVersionFormat`、`EmptyModId`、`ContradictoryMigrationInput`。
4. **B-4 Strict 策略 flags 终态：** 批准方案①——Strict 拒绝迁移时，最终 `Blocked`，flags := {`rejected`}，`reason_code = policy_rejected`。不修改规范。`needs_backup`/`may_lose_data` 仍按改写前管线结果计算；`may_auto_continue = false`。
5. **B-1a 依赖版本满足规则：** 批准沿用 `platform-core` 先例——依赖 `version_requirement` 采用 SemVer `VersionReq` 求值；非法表达式归入 `InvalidVersionFormat`。复用工作区已有 `semver` 依赖（save-manager `Cargo.toml` 已含），**零新增依赖**。
6. **InspectedSave 访问器：** 批准增加只读 `mod_payload(mod_id) -> Option<&[u8]>`，不借此扩展存档写入或恢复职责。

## 3. `LoadError` 构造点与传播顺序【已批准：planning/33 §4.1/§4.4/§4.5】

```text
inspect_save_file: fs::read 失败          → Io{stage:Read}
inspect_save(bytes):
  1. SaveLayout::from_bytes               → Layout(PartitionError)        [原样传播]
  2. verify(&layout)
       Err(IntegrityError)                → Integrity(..)                 [结构性]
       Ok(report) 且 !is_intact()         → Corrupted(report)             [到此为止]
  3. SaveManifest::from_bytes             → Manifest(SaveManifestError)   [原样传播；公开流程结构性不可达——所有 Manifest 解析失败已在步骤 2 经 verify 以 Integrity(..) 截获，见 §6 注（OWNER-DECISION-03）]
  4. system_manifest(&layout)             → SystemManifest(Missing|Invalid)
  5. 全部通过 ⇒ InspectedSave（构造即证据）
```

错误类型风格：手工 `Display`/`Error`/稳定码，不新增 thiserror。`LoadError::Manifest` 变体保留于类型定义作为传播链完整性声明，但公开流程结构性不可达（OWNER-DECISION-03）；不为此新增 `pub(crate)` 构造器、测试专用绕过路径或公开 API。

## 4. 判定流程（九步实现展开）【已批准：planning/33 §7；B-1~B-4 已落实】

```text
assess_compatibility(inspected, env):
  0. env 输入校验（确定性顺序）：
       a) EmptyModId（环境侧或存档侧）
       b) DuplicateModId（环境侧优先，存档侧次之）
       c) InvalidVersionFormat（§2.2 最小解析集合；首次失败即返回）
       d) ContradictoryMigrationInput（migration == NotRequired 但任一 schema 不等）
       → Err(CompatInputError)（判定不开始）
  1. [inspect 已完成] 结构+完整性                       → 损坏已在 LoadError 截获
  2. manifest.save_format_version ≤ SUPPORTED             → 否: Blocked+rejected
     【防御层（OWNER-DECISION-02）】正常公开流程中不可达：`save_format_version` 超出支持上限的存档在 `inspect_save` 的 `verify` 阶段即被拒绝（`LoadError::Integrity`，稳定码 `save.unsupported_format_version`），不会进入判定器；本步谓词保留为判定器内部的防御性规则
  3. kernel_api 精确匹配（数值对）+ platform 单向闸门      → 否: Blocked
  4. mods 集合比较（缺失/多余；版本仅诊断不作谓词）         → 缺失: Blocked+missing_dependency
  5. 依赖 VersionReq 求值 + kernel_api_requirement 精确匹配 → 不满足: Blocked
  6. world_schema_version 与各 mod schema_version 比较     → 有差异 → 步 7
  7. migration: Available⇒CompatibleWithMigration + requires_user_confirmation;
     Unavailable⇒Blocked(schema_mismatch_no_migration)
     （NotRequired 分支已在步 0 拦截）
  8. SAVE-002 一致性检查结论复用（浅落实）
  9. policy 终裁（§7）：
       Normal  ⇒ 管线结果原样输出
       Strict  ⇒ 管线结果 CompatibleWithMigration 改写为 Blocked + flags={rejected} + policy_rejected
       其他 verdict 原样
     + 填充 §13 字段与三布尔（§8）→ CompatibilityReport
```

短路规则：任一步失败即终止，`reason_code` 记录首个失败步。

【已批准】`degraded` / `discouraged` 零触发，契约测试断言其不出现（修订 b）。

**存档检查阶段稳定码与判定阶段原因码的区分（OWNER-DECISION-02）：** 未来格式版本（如 `save_format_version = 2.0`）由 `inspect_save` 前置拦截——`verify` 内部解析 Manifest 分区时触发 SAVE-001 语义校验，返回 `LoadError::Integrity(IntegrityError::Manifest(_))`，稳定码经 `IntegrityError::code_str()` 透传为 **`save.unsupported_format_version`**（SAVE-001 既有稳定码，非本包新增）。`LoadError::Manifest` 在此场景不可达（`verify` 先于 Manifest 步骤失败）。判定器步 2 谓词与原因码 `save.compat.unsupported_format_version` 保留为不可由公开 API 到达的防御层；不为此新增 `pub(crate)` 构造器或测试专用绕过入口。

**非法 Manifest 的错误路径（OWNER-DECISION-03）：** 任何 Manifest 解析失败（JSON 非法、Schema 结构违规、语义校验失败）在公开流程中均由 `inspect_save` 步骤 2 的 `verify` 内部 `canonical_view` 截获，返回 `LoadError::Integrity(IntegrityError::Manifest(_))`，稳定码经 `IntegrityError::code_str()` 透传为对应的 SAVE-001 稳定码——**具体码取决于测试输入**，例如：Manifest JSON 非法 ⇒ `save.invalid_manifest`（[lib.rs](file:///e:/Hexa%20Game%20Kernel/crates/save-manager/src/lib.rs) `from_bytes` 首步 JSON 解析失败，L392-398）；格式版本过新 ⇒ `save.unsupported_format_version`。`LoadError::Manifest` 为公开流程结构性不可达的防御性变体（`verify` 在同一份字节上先行失败，步骤 3 的重解析必然成功），保留该变体但不构造测试触发路径，亦不得经"篡改后重算摘要"伪装触发（`integrity::generate` 同样经 `canonical_view` 解析 Manifest，非法 Manifest 无法生成有效摘要）。

## 7. `LoadingPolicy` 判定语义【已批准：planning/33 §5.5 + B-4】

- `{Normal, Strict}` 穷尽冻结，不加 `#[non_exhaustive]`【已批准】。
- `Normal`：管线结果原样输出【已批准】。
- `Strict`：管线结果为 `CompatibleWithMigration` ⇒ 最终 `Blocked` + flags := {`rejected`} + `reason_code = policy_rejected`；其他管线 verdict 原样通过【已批准 B-4】。`requires_user_confirmation` 随 verdict 改写一并移除，确保终态落在规范 §5.4 映射表第 7 行（`Blocked + rejected`），无映射表外搭配。
- **机器可读诊断：** `policy_rejected` 唯一编码"迁移路径存在但被策略拒绝"；人类可读补充由 `available_actions` 承载（如"以 Normal 策略重新评估并确认迁移"）。

## 8. 三布尔计算基准【已批准：planning/33 §5.2 + B-4】

- `needs_backup` / `may_lose_data` 按**策略改写前**管线结果计算。
- `may_auto_continue` 按**策略改写后**最终结果计算：仅当最终 verdict ∈ {`Compatible`, `CompatibleWithMigration`} 且无 `rejected` / `discouraged` / `requires_user_confirmation`。
- Strict 拒绝迁移 ⇒ 最终 `Blocked` ⇒ `may_auto_continue == false`；`needs_backup` / `may_lose_data` 不因策略拒绝消失。

## 9. 迁移确认语义【已批准：planning/33 §5.6A 修订 a/d + B-4】

所有 `CompatibleWithMigration` 场景均附挂 `requires_user_confirmation`，且 `may_auto_continue == false`（Normal 与 Strict 一致）。调用方见到 `CompatibleWithMigration` 必伴随确认请求，不得自动继续。Strict 闸门将 verdict 改写为 `Blocked` 后，`requires_user_confirmation` 已移除，但仍通过 `policy_rejected` 保留"迁移原本可用"的机器可读信息。
