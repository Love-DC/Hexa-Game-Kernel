## 三、F-4 裁决提案：版本模型集合

### 3.1 冲突事实
| 规范 | 分离的版本集合 |
|---|---|
| `Save & Compatibility Specification` §3.4 | **6 项**：Save Format / World Schema / Mod Schema / **Platform Version** / Kernel API Version / Mod Version |
| `Game Kernel — 完整项目规范` §6.2 | **5 项**：Save Format / **Kernel State Schema** / Mod Data Schema / **Game Definition Version** / **API Version** |
| `Project Architecture` §7 | **7 项**：save file format / world-state schema / Mod-owned persistent schema / **Mod code version** / Kernel API version / **Runtime version** / **Migration implementation** |

### 3.2 候选方案

**方案 D1（推荐）：以 Save 规范 §3.4 为存档域权威集合 + 显式同义映射表**
- 内容：`SAVE-001` Manifest 的版本字段以 §3.4 的 6 项为准；对另两规范中的同义/近义项建立**映射**（不新增字段）：
  - World Schema（§3.4）= Kernel State Schema（§6.2）——同义。
  - Mod Version（§3.4）= Mod code version（Arch §7）——同义。
  - Platform Version（§3.4）⊇ Runtime version（Arch §7）——待确认是否合并或并列。
  - Game Definition Version（§6.2）——**不并入版本集合**，而作为**独立元数据字段**处理（见 F-5）。
  - Migration implementation（Arch §7）——属**迁移实现标识**，非存档元数据（归 `SAVE-006`）。
- 取舍：权威清晰、字段不膨胀；需维护一张跨规范映射表；Platform/Runtime 边界需一次确认。
- 影响：`SAVE-001` 字段集稳定为 6 项 + `game_definition`（F-5）。

**方案 D2：取三规范并集（约 8～9 项）**
- 内容：Save Format、World/Kernel State Schema、Mod Schema、Game Definition、Platform、Runtime、Kernel API、Mod Version、Migration implementation 全部纳入。
- 取舍：覆盖最全；但引入跨域字段（Migration implementation、Runtime），与"存档元数据"语义不符，且易在后续规范再变动时失配。
- 影响：Manifest 变大，语义边界模糊。

**方案 D3：以完整项目规范 §6.2 为上位权威（5 项）**
- 内容：`SAVE-001` 按 §6.2 的 5 项实现。
- 取舍：与"总规范优先"一致；但 §6.2 缺 Platform Version、且其"API Version"表述比 Save §3.4 粗，会与 §3.4/§13 的机器可读要求错位。
- 影响：与 Save 域规范 §3.4 冲突未消。

### 3.3 推荐
**采用 D1。** 理由：① Save 规范是该域唯一权威（§0:22"本文与……共同构成工程合同"），且 §3.4 是存档版本模型的定义处；② 映射而非合并，避免字段膨胀与跨域污染；③ 与 F-5 分工清晰（版本集合 vs 元数据字段）。

### 3.4 待确认子项
- Q-F4-a：`Platform Version`（§3.4）与 `Runtime version`（Arch §7）是否合并为一个字段？
- Q-F4-b：同义映射表是否需写入 Save 规范勘误（作为规范修订）？

## 四、F-5 裁决提案：`game_definition` 字段

### 4.1 冲突事实
- Save 规范 §3.2 必需元数据**未含** Game Definition；§3.3 示例亦无。
- 完整项目规范 §6.1（L494）"存档必须能够说明自己由什么游戏定义……产生"、§6.3（L515）列出"Game Definition 标识与版本"、L140"不得默认不同游戏定义之间可以共享存档"。

### 4.2 候选方案

**方案 E1（推荐）：`SAVE-001` Manifest 纳入必填 `game_definition {id, version}`**
- 取舍：满足完整规范要求、支撑跨 Game Definition 兼容判定；Manifest 增一字段。
- 影响：与 F-4 的"版本集合"分离（此为**标识字段**，非版本模型项）。

**方案 E2：不纳入，登记延后并记录理由**
- 取舍：保持与 Save §3.2 字面一致；但无法满足完整规范 §6.1/§6.3，且 L140 的跨 Game Definition 隔离缺乏数据基础。
- 影响：`SAVE-005` 判定跨 Game Definition 时缺输入。

**方案 E3：纳入 `game_definition` 但允许 `null`（表示通用/未声明）**
- 取舍：兼容单 Game Definition 早期场景；但"未声明"与"禁止默认共享"存在张力，需策略配合。
- 影响：判定逻辑需处理空值分支。

### 4.3 推荐
**采用 E1。** 理由：完整规范的 MUST 级要求（§6.1/§6.3）+ L140 隔离原则；字段语义明确、实现成本低。

### 4.4 待确认子项
- Q-F5-a：`game_definition` 是否对所有存档必填？若早期单 Game Definition 场景，是否允许 `null`（即退化为 E3）？

## 五、F-6 裁决提案：确定性运行配置字段

### 5.1 冲突事实
- Save 规范 §3.2（L156）将"与确定性恢复相关的运行配置"列为**必需元数据**；但 §3.3 示例 Manifest（L165-191）**未包含**该字段；`planning/22` §五.1 字段清单亦未含。

### 5.2 候选方案

**方案 F1（推荐）：`SAVE-001` 定义并纳入 `simulation_config` 字段（值可先占位）**
- 内容：`SAVE-001` 定义该字段的结构（用于承载确定性恢复所需配置），本轮允许其为空/占位，具体值由 `SAVE-004`（一致快照与保存）填充。
- 取舍：满足 §3.2 必需项、字段归属清晰；`SAVE-001` 需定义一个暂无实际值的结构。
- 影响：与 `SAVE-004` 的接口需一致；`SAVE-001` 仍为纯内存（不填真实配置）。

**方案 F2：`SAVE-001` 不纳入，延后至 `SAVE-004`**
- 取舍：`SAVE-001` 更"纯"；但违反 §3.2（MUST 级必需元数据），版本模型包缺该字段定义。
- 影响：Manifest 模型与规范 §3.2 不一致。

**方案 F3：纳入字段但标注"可选、后续填充"**
- 取舍：折中；但 §3.2 为必需项，"可选"表述与规范冲突。

### 5.3 推荐
**采用 F1。** 理由：§3.2 为 MUST 级必需元数据，`SAVE-001` 作为"存档 Manifest 与版本模型"包应承载其**定义**；值填充归 `SAVE-004`，职责不越界。

### 5.4 待确认子项
- Q-F6-a：字段命名（`simulation_config` / `determinism_config` / 其他）？
- Q-F6-b：是否同时提请修正 Save 规范 §3.3 示例（补该字段），以消除 §3.2 与 §3.3 的文字不一致？（属规范勘误，需单独授权。）

## 六、F-7 裁决提案：兼容性结论分类

### 6.1 冲突事实
| 规范 | 分类 |
|---|---|
| Save §5.1 | **4 类（机器级）**：`Compatible` / `CompatibleWithMigration` / `Blocked` / `Corrupted` |
| 完整 §6.8 | **7 类（用户/策略级）**：可直接加载 / 需要迁移 / 需要用户确认 / 需要补充依赖 / 存在功能降级 / 不建议加载 / 必须拒绝加载 |

### 6.2 候选方案

**方案 G1（推荐）：双层分类——机器级 4 类 + 用户/策略级 7 类 + 映射表**
- 内容：`SAVE-005` 输出 Save §5.1 的 4 个**机器可读码**（§13 要求机器可读）；同一结果附带策略/用户级细化标记以覆盖 §6.8 的 7 项；建立映射表。
- 候选映射（**待批准，非最终**）：

  | 完整 §6.8（用户/策略级） | Save §5.1（机器级） | 说明/原因码 |
  |---|---|---|
  | 可直接加载 | `Compatible` | 无需迁移 |
  | 需要迁移 | `CompatibleWithMigration` | 有已验证/已授权迁移路径 |
  | 需要用户确认 | `CompatibleWithMigration` 或 `Blocked` | 取决于授权状态（未授权→`Blocked`） |
  | 需要补充依赖 | `Blocked` | 如 §13 示例 `SAVE_MOD_REQUIRED_MISSING` |
  | 存在功能降级 | `Compatible`（带降级警告码）或 `CompatibleWithMigration` | 可加载但功能受限 |
  | 不建议加载 | `Blocked`（带警告） | 存在不允许自动处理的冲突 |
  | 必须拒绝加载 | `Blocked` / `Corrupted` | 结构/完整性失败→`Corrupted` |

- 取舍：保留机器可读稳定性、又表达策略粒度；需维护映射与细分级枚举。
- 影响：`SAVE-005` 的输出结构 = 4 码 + 细化标记（+ 原因码）。

**方案 G2：统一为 7 类**
- 取舍：表达力最强；但与 Save §5.1/§13 的"机器可读码"计数不一致，需改 Save 规范。
- 影响：改动规范正文（超出当前授权）。

**方案 G3：统一为 4 类**
- 取舍：与 Save 一致、最简；但 §6.8 的"用户确认/补充依赖/功能降级/不建议加载"需挤入原因码，语义拥挤。
- 影响：用户/策略表达弱。

**方案 G4：两条独立不映射**
- 取舍：不动规范；但产生歧义（同一存档两套结论），违背"必须登记冲突"原则。
- 影响：不可接受。

### 6.3 推荐
**采用 G1。** 理由：Save §5.1 是机器可读码权威（§13:727 要求机器可读结果），完整 §6.8 是用户/策略粒度；**映射而非合并**，兼顾稳定码与表达力。

### 6.4 待确认子项
- Q-F7-a：映射表是否随 `SAVE-005` 冻结为契约测试？
- Q-F7-b：细分级枚举命名与"是否需要备份/是否可能丢数据/是否允许自动继续"（§13:738-740）字段如何并列？
