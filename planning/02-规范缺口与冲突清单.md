## 2. Kernel 与确定性

| ID | 状态 | 发现与证据 | 影响 | 处理建议 / 关口 |
|---|---|---|---|---|
| GAP-04 | 待具体化 | Kernel Contract §3 规定 Tick 原子性，§6.3 又允许外部命令逐条成功并保留；当后续发生不可恢复核心错误时，前序写入如何回滚/不可见尚未落到算法。 | 可能出现 Tick 返回失败但权威 World 已局部改变。 | 定义 staging/commit 点、观察者可见时间、回滚范围；对每个阶段注入故障并验证。P1 前冻结。 |
| GAP-05 | 待具体化 | 外部命令跨来源的“权威排序键”交给 Platform 和多人规范；多人正文缺失，序号分配/重复重放/重连也未定义。 | 同一输入集可能因来源顺序不同产生不同世界。 | 先定义可序列化排序键；P1 单机使用固定来源与序号，P5 联机复用并验证同一算法。 |
| GAP-06 | 待具体化 | Kernel 提到 Rust 类型和 Rust 风格接口，同时称签名是意图示例；仓库没有工具链或 Rust 配置。 | 实现语言和 SDK ABI 尚不能假设已经正式决定。 | 工程基线记录语言选择及理由。当前建议 Rust，利用现有契约意图；具体版本按项目启动时验证并锁定。 |
| GAP-07 | 待具体化 | 确定性要求有随机数状态、稳定排序、规范哈希原则，但算法/序列化/数值语义未定；跨平台边界也未定。 | `StateHash` 相等的意义和支持平台无法验收。 | P1 先锁定单一构建/运行配置下的规范化结果；跨平台矩阵和浮点路径在 P2/P5 基准后批准。 |
| GAP-08 | 待具体化 | System 失败可隔离 Mod，但未明确继续调度条件、必需 System/Mod 失败后的暂停规则、已经产生的事件/命令处理。 | 静默漏掉权威操作或扩大为不必要的整个世界停机。 | 定义失败分类、未提交输出撤销、依赖闭包影响及恢复入口；故障注入覆盖。 |
| GAP-09 | 待具体化 | Event 允许命令、System 领域事件及 Platform 输入事实产生；载荷 Schema、大小预算、订阅生命周期和事件触发执行时机尚未定义。 | Event 可能成为隐式递归写入通道，或不同平台消费顺序不一致。 | MVP 只输出 Tick 封存记录，不实现递归事件回调；先冻结类型、顺序和限制。 |

## 3. Platform、存档和安全

| ID | 状态 | 发现与证据 | 影响 | 处理建议 / 关口 |
|---|---|---|---|---|
| GAP-10 | 待具体化 | Mod Manifest、API Registry、mod-lock、存档清单及迁移日志均有示例，没有正式 Schema/未知字段策略/稳定错误码。 | 工具和运行时可能对同一文件得出不同解释。 | 按格式分别建唯一 Schema、版本策略和正反例契约测试；先完成 MVP 用到的子集。 |
| GAP-11 | 需对齐 | 项目任务书偏好“声明式内容/游戏逻辑/Game Definition/Platform/原生”；Architecture 采用 Content/System；Mod Platform 的 `kind` 示例是 `content`、`system` 等。 | Manifest 类型术语与权限无关但名称不统一，SDK 文档容易分叉。 | 统一规范枚举，并明确类型描述职责、不自动授予权限。 |
| GAP-12 | 待具体化 | Mod Platform 建议 Wasm，但尚未指定引擎、ABI、确定性限制、燃料度量、内存/超时策略和升级兼容方式。 | 脚本 Mod 的可执行性、安全和重放无法证明。 | P1 做最小运行时技术验证；选定后记录版本和 Host API；不可信原生代码默认禁用。 |
| GAP-13 | 待具体化 | `save` 规范定义两阶段迁移，但文件容器、规范化序列化、摘要、提交/崩溃恢复及迁移器接口未定。 | 迁移失败可能破坏唯一存档，或不同版本产生不同结果。 | P1 只做受控快照保存/恢复；P3/4 再实现副本迁移、提交日志和故障恢复测试。 |
| GAP-14 | 缺失 | 没有 Security/Performance/Diagnostics 专章；现有 Mod 规范有原则和预算种类，没有信任分级、权限策略格式和基准数值。 | 安全承诺过强、性能目标无法量化。 | 对信任、权限和资源预算单独成规范；数值必须引用可复现硬件/负载测量，不能先承诺。 |

## 4. 模块/API 边界

| ID | 状态 | 发现与证据 | 影响 | 处理建议 / 关口 |
|---|---|---|---|---|
| GAP-15 | 待具体化 | Kernel Contract 的公开类型表指出 `CommandId`、`ComponentTypeId`、`ResourceTypeId`、`EventRecord`、`StateHash` 等仍要具体定义；World 查询、值编码和读写声明也未成型。 | Platform、Wasm Host、存档和 SDK 会各自建类型。 | P1 形成一个唯一 Kernel API 类型源，并用契约测试约束调用方。 |

## 5. 一致性结论

目前没有证据显示 Kernel、Platform、Save 三份正文在总体边界上互相否定：Platform 持有 Mod/兼容决策，Kernel 持有权威模拟状态，存档服务通过快照接口工作，这三者方向一致。需要在实现前关闭的是上表中的交互语义和可验证细节，尤其 GAP-04、05、07、08、10、12。
