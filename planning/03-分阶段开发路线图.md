# 分阶段开发路线图

- 状态：建议路线，第一阶段实现范围待项目负责人确认
- 原则：先关闭高风险契约，再建立最小端到端闭环；每一阶段都以可运行产物和自动验证过门

## 阶段总览

| 阶段 | 目标 | 主要交付 | 进入下一阶段的门槛 |
|---|---|---|---|
| P0 资料审查与范围确认 | 盘点现有规范、记录缺口、确认第一个可交付范围 | 现状/架构/缺口/路线图/任务卡/决策/流程七份文档 | 负责人确认 P1 范围；没有被误称为已实现的项目状态。 |
| P1 最小垂直切片 | 证明一个确定 Tick、一个受控 Mod、一个可恢复世界状态能端到端工作 | 工程骨架、最小 Kernel、Command/System/Event、最小 Mod、快照/哈希、CI 和验收报告 | 所有 P1 验收项在本地和 CI 通过；失败注入不破坏快照；文档/实现一致。 |
| P2 Kernel 契约硬化 | 完善类型、调度/访问模型、事务语义、错误和确定性 | 唯一 Kernel API、契约测试、故障分类、规范化序列化和稳定哈希 | Kernel 契约无未处理的 P0 缺口；支持模式和状态摘要边界可复现。 |
| P3 Mod Platform 基线 | 建立正式 Manifest、依赖解析、锁文件、生命周期、权限及 API Registry | 正式 Schema、Resolver、生命周期状态机、受控运行时、诊断工具 | 依赖/权限/运行时失败场景可自动拒绝或恢复；安装内容与锁文件一致。 |
| P4 存档、兼容与重放 | 长期保存、迁移与分歧定位 | 存档格式、快照恢复、迁移事务、迁移日志、黄金存档与输入重放 | 原档保护、迁移失败恢复、重复加载不重复初始化、重放差异可定位。 |
| P5 联机权威与会话 | 在确定性边界上实现服务器权威输入和会话管理 | Multiplayer 规范、服务器输入验证、客户端同步、锁定 Mod 配置、断线恢复 | 多人契约补齐；版本/摘要错配在模拟前阻止；同步与重连测试通过。 |
| P6 SDK、Launcher 与参考游戏 | 让开发者和玩家能构建、验证、加载并诊断 Mod | CLI/SDK、Manifest 校验、兼容检查、调试工具、Launcher 体验、官方最小 Game Definition | 示例 Mod 完成从创建到发布教程；普通玩家能理解兼容性与恢复提示。 |
| P7 安全、性能与社区试用 | 以真实工作负载验证安全、容量和长期运行 | 安全/性能/诊断规范，300+ Mod 配置基准，故障/长稳测试，社区反馈 | 仅发布测得数据；严重故障与存档损坏路径有恢复结果；社区阻塞问题有处置。 |

## P0：本轮规划交付

### 目标与前置条件

读取实际工作区和用户任务书；不假设缺失文档存在。当前审查结果及七份交付文件作为 P0 产物。

### 验收

- 五份现有 Markdown 资料均纳入盘点；清楚标注缺失的四份规范。
- 文档方案区分设计、待验证、实现和验收状态。
- 任务卡有依赖、范围、测试和验收标准。
- 第一阶段明确排除项，等待负责人确认后才执行。

## P1：最小垂直切片

### 范围

- 建立可复现工程基线和自动测试入口。
- Kernel 能按固定 Tick 规则推进极小权威状态。
- 一个最小 System 通过 Command 改变状态，Event 只报告已提交事实。
- 处理并加载一个测试 Mod；建议以受限、确定性 Wasm 路径验证执行边界。具体运行时由工程验证选择。
- 保存/恢复世界，继续执行后获得可比较的 StateHash。
- 提供清晰错误，自动测试覆盖正常、拒绝、失败恢复。

### 不在范围内

完整 UI/Launcher、Mod 商店、热加载、正式联机服务、复杂游戏玩法、第三方原生代码、300+ 性能承诺、全面迁移市场和跨平台逐位确定性声明。

### 测试与验收

使用《第一阶段详细任务卡》中的逐项门槛。不得用 stub/占位功能宣称通过端到端要求；测试命令和真实结果在交付报告中记录。

## 后续阶段的依赖说明

1. P2 依赖 P1 确认的模块骨架和可重复状态转换。
2. P3 依赖 Kernel API 的唯一类型定义；P1 运行时只做最小 Host API，不提前扩展全部 SDK。
3. P4 依赖稳定 World 导出/恢复接口、数据所有权和格式版本。
4. P5 依赖 P2 的输入排序、确定性边界及 P3 的锁定配置；P5 启动前必须取得 Multiplayer 规范正文或完成新的明确审查/批准。
5. P6 依赖可用的 Mod Validator、锁文件和诊断接口。
6. P7 的“300+”验收必须先定义 Mod 配置组成、目标硬件、启动时间/内存/Tick 分布和测量方法；没有这些输入不设虚构阈值。

## 阶段门禁

阶段结束时由 AI 提交：交付文件/提交、变更摘要、执行过的命令及结果、未执行项目及原因、已知风险、验收逐项证据。下一阶段只在门槛通过后开始；项目负责人只需要处理决策清单中标注为“需确认”的问题。
